# prototype_review：习惯匹配

复审目标：检查 3 条产品路径是否忠实表达 `product_brief.md`，是否违反不可虚构边界，是否可进入交付。

## 总 verdict

可通过，推荐以 **方案 A：快速匹配** 作为第一版主路径，吸收方案 B 的推荐理由表达，不采用方案 C 的完整时间排布作为首版主流程。

## 策略复审

- A 快速匹配最贴近主目标“提升第一周计划激活率”。
- B 信任报告能补足推荐可信度，但如果单独作为主路径，可能增加阅读负担。
- C 先排时间解决真实可执行性，但输入成本偏高，适合作为“调整计划”或第二步。

## 信任 / 风险复审

- 通过：所有方案都避免健康结果承诺。
- 需保留：推荐理由必须写成“基于你提供的信息”，不能写成确定能力。
- 风险：如果后续加入历史打卡数据，需要提示用户数据不足时的默认逻辑。

## 设计系统复审

- 通过：移动端首屏任务清晰，主 CTA 单一。
- 需修正：A 的推荐卡不能过度使用抽象渐变和大面积空白；要像真实产品功能页。
- 不需要重出：问题属于 prompt 细化，不影响产品路径判断。

## 数据可行性复审

- 可用字段：时间安排、目标、历史打卡。
- 不可写入：心率、睡眠、饮食、教练评分。
- 待补充：历史打卡是推荐增强项还是必需项。

## 交付建议

进入 `$pm-handoff`，输出产品设计文档。推荐方案写为：快速匹配为主路径，推荐理由采用信任报告的三段证据结构，时间排布保留为调整入口。
