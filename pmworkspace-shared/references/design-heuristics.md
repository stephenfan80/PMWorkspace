# 设计启发

产品追问和产品方向审查后使用这些启发。它们把产品意图转成页面级设计选择。

## Product Strategy

- Start from the metric, not the component.
- A good prototype makes the user's next action feel obvious and valuable.
- Every screen should have a job: inform, compare, decide, submit, recover, configure, or monitor.
- The first screen should answer the user's strongest "why continue?" question.
- If the product requires human follow-up, fulfillment, or manual confirmation, explain why and what will be confirmed.
- Do not hide basic information that the product should reasonably provide for free.

## Value Boundary

When an action costs the user time, attention, permission, identity, money, or personal data:

- Show a useful preview before the costly action.
- Make the post-action value more specific, reliable, saved, shared, or confirmed.
- Keep the exchange fair: the user should understand what they get and why the action is needed.
- If the action is not justified, redesign around free information first.

## Form Page

- Keep one dominant conversion action.
- Ask for the minimum input needed before the action.
- Move optional or precision-improving conditions after submit or into a secondary step.
- Use a concrete value hook, not generic "submit to learn more" copy.
- Show masked or partial values when full details require submission.
- Avoid stacking many chips, selectors, disclaimers, and secondary actions above the primary button.
- If the product is not a lead or signup flow, do not invent a phone/email field.

## Result Page

- First fulfill the promise from the form.
- Use an integrated summary area before details.
- Make numbers, statuses, and explanations align visually.
- Show the "final" or most decision-useful value when the task involves price, eligibility, risk, or fit.
- Put optional refinements, detailed conditions, and follow-up explanation here rather than on the form.
- If follow-up contact happens, state who will contact the user, when, why, and what they will confirm.

## Tool And Workflow Page

- Optimize for repeated task speed and error recovery.
- Show state clearly: loading, empty, partial, error, success, and stale data.
- Put frequent actions close to the object they affect.
- Avoid decorative modules that do not improve task completion.

## Transaction Or Service Flow

- Make eligibility, required documents, cost, status, and next step explicit.
- Show what is confirmed versus pending.
- Include recovery paths for ineligible, unavailable, expired, or failed states.
- Avoid promising fulfillment that depends on unavailable data or operations.

## 看板或数据分析页

- Start with the decision the user needs to make.
- Show comparison baselines and data freshness.
- Label estimates, samples, delayed data, and missing data.
- Avoid charts that do not change a decision.

## Iteration From Annotated Screenshots

- Treat red boxes as remove or revise targets unless the user says otherwise.
- Treat green boxes as keep or simplify targets unless the user says otherwise.
- Preserve accepted style and structure outside the annotated regions.
- If the user asks for a corresponding result page, move removed form complexity into result-page value modules.

## Multi-Scheme Design

Make schemes meaningfully different:

- Hook difference: price certainty vs risk reduction vs convenience vs eligibility vs comparison.
- Information architecture difference: preview-first vs form-first vs progressive disclosure.
- Interaction difference: one-step submit vs tabs vs comparison cards vs result report.
- Trust model difference: free answer first vs personalized confirmation vs expert/human verification.

Do not generate three visual skins for the same idea and call them three schemes.
