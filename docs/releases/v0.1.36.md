# PMWorkspace v0.1.36

PMW v0.1.36 adds the Runtime Operation Router.

## What Changed

- Added `pmw-operation-router classify` between `pmw-trigger-guard` and `pmw-controller intake`.
- Updated `pmw-trigger-guard` so PMW hits now require `pmw-operation-router classify` when the router is available.
- Added `pmw-controller continue-operation` for flow-loop operations such as prototype revisions.
- Added operation identity fields: `operation_id`, `operation_type`, parent run/task/revision, source image, artifact id, edit scope, preserve scope, and inherited context.
- Added operation-scoped dashboard and image preflight support for `prototype_revision`.
- Added operation-scoped image permits bound to `operation_id`.
- Updated routing/runtime/readiness/image-prompt docs and generated skill contracts.
- Added P0 eval coverage for new workflow routing, short answers, prototype revisions, source image blockers, design spec inheritance, operation permits, and no generic fallback.

## Product Impact

PMW no longer treats every PMW-triggered message as a new product workflow. New product tasks still run the full deep alignment chain. Flow-loop actions now use the smallest correct gate:

- “确认策略审查” -> `pmw-controller answer`
- “确认没有问题” -> `pmw-controller lock-brief`
- “在这个图基础上修改，不要改 100 元券样式” -> `pmw-controller continue-operation --operation-type prototype_revision`
- boundary-changing feedback -> brief relock

This keeps hard gates intact while avoiding repeated goal-mode, AutoDesign, product-direction, and strategy replay during local prototype edits.
