PMW
PMWorkspace 执行逻辑图 产品专家增强器：先对齐事实，再判断路径，最后出可信原型与交付稿
适用版本：0.1.18 · HTML 静态图谱

PMW 不是“听到需求就出图”，而是把用户临时增强成更强的产品人。

这份图把 PMW 的执行逻辑整理成一张可运行的工作台地图：先建立统一产品上下文，识别全新功能或已有功能迭代，再通过产品方向审查、产品简报、准备度门槛、image-2 原型、原型复审和交付资产逐步推进。任何时候，只要事实、证据、承诺或视觉基线不足，就回到最早能修复的门槛。

1
先收束上下文

每个技能开始先建立产品信息对齐包，不能只凭最后一句话继续下游。

2
先挑战判断

真实问题、现状替代、当前损失和反指标未清楚前，不把功能愿望包装成方案。

3
先过门槛再出图

产品简报未已对齐、视觉基线未接收、设计规范目标缺失或 readiness 不通过，都不写 image-2 prompt。

四、产物流动

PMW 的下游技能不靠对话记忆接力，而靠可读产物和本地审计资产接力。

product_brief

产品简报：真实问题、证据边界、选中路径、反指标、不可虚构项、原型范围。

browser_evidence / visual_baseline

线上参考、设计启发、截图基线、目标输出像素和保留区域。

三条产品路径、输出单元、设计规范目标、image-2 单图绑定。

五、真实运行防错规则

这些规则对应实际体验中最容易跑偏的地方。

一个 D 不能直接出图

用户选择一个方向，只代表方向候选成立，不代表产品简报、线上基线、反指标和不可虚构项已对齐。

截图不是自动出图授权

截图先作为视觉基线和证据输入，PMW 要先拆当前优势、问题区域、保留项与可改项。

新图必须优于线上

已有功能迭代不能因为“新”就通过。必须说明改了哪里、保留了什么、为什么比线上更好。

假设可以推进，但要标明

缺数据或访谈可以做假设原型，但必须写“未验证风险”，并带入复审和交付边界。

设计灵感不能替代产品路径

Dribbble、Pinterest 或平台模式库只能提升表达质量，不能把不同视觉风格伪装成三条产品路径。

产品作业卡优先

PMW 应展示当前主阻断和关键缺口队列，并给出产品建议与信息架构建议；当前轮先处理主阻断，但不能暗示只补一项就足够。

六、关键判断清单

这组判断决定 PMW 下一步走哪个技能，而不是机械执行固定流程。

D0 产品路径

全新功能还是已有功能迭代？已有功能必须先要线上视觉基线；全新功能必须先压实目标用户、触发场景、当前替代和当前损失。

D0 执行深度

快速成型还是深度交付？生产流程、高风险承诺、线索/交易/隐私、真实数据或研发交付信号会升级深度交付。

范围模式

扩大、选择性扩大、保持、收缩或转向。范围、承诺、实验口径或交付责任变化必须让用户显式拍板。

出图判断

只有已对齐产品简报、方案方向确认、设计规范目标、不可虚构项和 readiness 通过时，才能写 image-2 prompt。

复审判断

图是否解决真实问题，是否把假设画成事实，是否违背反指标，是否优于线上，是否存在不可虚构承诺。

交付判断

交付稿只写已确认事实；未确认的数据、算法、接口、库存、价格、权益或合规能力不能进入验收承诺。
