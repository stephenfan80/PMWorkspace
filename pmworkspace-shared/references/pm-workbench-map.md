# PMWorkspace 端到端工作台地图

本文件是 PMWorkspace 的全链路地图。它把 README 的产品叙事、`routing.md` 的下一技能选择、`pm-eval-system.md` 的 fixture 分类，以及各技能输出的状态字段统一到同一张表里。

使用优先级：

1. `routing.md` 仍是路由唯一真源。
2. 本文件是链路阶段、状态字段和 eval 分类真源。
3. 各技能自己的 controller 文档负责阶段内细节。

## 端到端链路

| 阶段 | 负责技能 | 目标 | 必备输入 / 事实来源 | 统一状态字段 | 不可越过门槛 | 产物 / 下一状态 | Eval 分类 |
|---|---|---|---|---|---|---|---|
| 0. 欢迎与 D0 路由 | `$pm-workspace` | 判断快速成型或深度交付，并创建/复用 run | 用户任务、输入材料、风险信号、当前 run | `当前模式`、`当前门槛`、`下一技能`、`为什么`、`run_id`、`证据状态` | 模式不清、风险冲突、输入不足时必须问一个 `D0` | 路由结果，进入最早缺失技能 | `pm-workspace-entry`、`pm-workspace-routing`、`pm-workspace-runtime` |
| 1. 自动产品评审 | `$pm-autoplan` | 以靠谱产品负责人姿态串联推荐链路，但只推进到最早可靠门槛 | D0 模式、用户目标、现有 brief / Zoon / run 证据 | `自动评审结论`、`我建议`、`理由`、`状态`、`run_id`、`模式`、`模式来源`、`推进阶段`、`当前门槛`、`最早门槛`、`门槛等级`、`门槛来源`、`停止原因`、`下一技能`、`交接上下文`、`证据状态页` | 快速成型遇到生产流程、高风险承诺、真实数据、线索/交易/隐私或交付信号时升级深度交付 | 轻量包假设确认，或带交接上下文交给下一个技能 | `autoplan`、`quick-shaping`、`deep-delivery` |
| 2. 产品价值澄清 | `$pm-jobs` | 把功能愿望澄清成产品价值判断，并只问一个最有价值的 Q / D | 用户、触发时刻、现状替代、当前损失、目标、反指标、约束、线上参考状态 | `产品价值判断`、`我现在判断`、`当前价值缺口`、`为什么这是最该问的一刀`、`这个答案会影响`、`状态`、`run_id`、`模式来源`、`诊断阶段`、`当前最大缺口`、`Q 预算`、`停止原因`、`下一技能`、`证据状态`、`当前 Q`、`当前 D` | 缺事实先问 `Q`；事实足够但取舍会改方向时才问 `D`；每轮只展开一个；功能愿望不能直接当成核心问题 | 前提确认，或交给策略审查 / 产品简报 | `pm-jobs` |
| 3. 策略审查 | `$pm-strategy-review` | 判断方向应扩大、保持、收缩还是转向，并把最大策略矛盾转成 PM 取舍 | `$pm-jobs` 交出的事实、风险门槛、反指标、不可虚构项 | `策略审查结论`、`我建议`、`最大策略矛盾`、`建议姿态`、`为什么`、`当前必须拍板`、`进入产品简报的写法`、`run_id`、`来源门槛`、`策略风险类型`、`使用视角`、`产品动作`、`策略取舍`、`范围外`、`用户承诺边界`、`反指标保护`、`对原型的影响`、`当前 D`、`下一技能`、`证据状态` | 基础事实缺失退回 `$pm-jobs`；改变范围/承诺/实验/交付责任时只问一个 `D`；每个审查视角必须落成产品动作 | 已拍板策略写入产品简报 | `pm-strategy-review` |
| 4. 产品简报 | `$pm-brief` | 压缩产品判断并固化门槛，生成产品核心信息契约 | 上游 Q/D、已确认前提、策略决策、Zoon 最新内容、线上参考、轻量检索 | `产品核心信息`、`一句话判断`、`目标用户 / 场景`、`核心问题 / 当前损失`、`当前替代方案`、`本次目标`、`反指标`、`策略选择`、`原型重点`、`不可虚构项`、`产品简报门槛`、`run_id`、`版本`、`确认状态`、`来源门槛`、`缺失门槛`、`支持信息`、`线上参考`、`Zoon`、`下一技能`、`证据状态` | 未完成前提确认、关键 D、线上参考或 Zoon 漂移时不能标为 `已对齐`；缺事实不能用简报补写 | `已对齐` 产品核心信息契约，进入原型或交付 | `pm-brief` |
| 5. 原型方案 | `$pm-prototype-shotgun` | 作为 image-2 原型出图导演，基于已对齐 brief 逐张生成每个方案/屏幕独立设计稿 | 已对齐 brief、Zoon 快照、线上参考、设计系统、prototype-board | `run_id`、`原型出图判断`、`产品简报`、`Zoon 事实来源`、`图片生成前门槛`、`方案差异质量`、`方案方向确认`、`图片输出单元`、`输出单元清单`、`单图生成协议`、`方案比较板`、`image-2 状态`、`证据状态` | 未已对齐、Zoon 实质漂移、线上参考缺失、方案只换皮、image-2 不可用时不能写提示词或替代出图；一次 image-2 调用只能生成一张图、一个方案和一个屏幕任务 | 独立原型图片，状态 `可进入原型复审` | `pm-prototype-shotgun`、`prototype-shotgun`、`prototype-output-contract`、`multi-scheme`、`production-reference`、`screenshot-feedback` |
| 6. 原型复审 | `$pm-prototype-review` | 判断图片是否可通过、需要重出、需要 PM 拍板或补参考，并把用户反馈资产化 | 原型图片、输出单元绑定、brief、Zoon、线上参考、设计系统、PM Review Army、用户全局记忆 | `run_id`、`产品简报 / Zoon 来源`、`Zoon 漂移检查`、`复审输入`、`输出单元绑定`、`证据状态`、`PM Review Army`、`逐屏结论`、`需要重出的屏幕`、`需要 PM 拍板`、`当前 D`、`偏好记忆更新`、`反馈资产化`、`下一技能` | 缺绑定不能凭视觉通过；违反 brief / 反指标 / 不可虚构 / 线上参考 / 设计系统必须重出；产品承诺未决必须拍板；事实错误、未决承诺和参考缺失不能保存成普通偏好 | `可通过` 原型，或修复 brief / D / 补参考；个人偏好、产品认知或 PMWorkspace 进化候选写入本地资产 | `prototype-review` |
| 7. 产品交付 | `$pm-handoff` | 把已通过复审的方向转成 PRD / 设计 / 实验 / 研发交付稿 | 已对齐 brief、已选原型、复审结论、D 决策、线上参考 | `run_id`、`交付目标`、`事实来源`、`交付前门槛`、`原型复审状态`、`未决拍板`、`交付类型`、`验收写入边界`、`下一技能`、`已保存资产`、`证据状态` | 未复审不交付；关键 D 未拍板不写验收；不可虚构项和未验证数据不能写成验收 | handoff 资产，状态 `可交付` | `pm-handoff` |
| 8. 运行与记忆 | 共享脚本 | 保存可审计状态，复用偏好但不覆盖事实 | `pmw-run`、`pmw-dashboard`、`pmw-prototype-board`、`pmw-memory`、`pmw-log` | `run_id`、`项目名称`、`证据状态`、`已记录决策`、`产物清单`、`偏好来源`、`建议下一步` | 历史偏好不能覆盖本轮 brief、Zoon、反指标、不可虚构项或当前门槛 | 本地审计轨迹、偏好、学习和 eval 结果 | `memory`、`decision-principles`、`eval-system` |

## 共享状态字段

所有用户可见输出尽量保留这些基础字段；阶段字段可以追加，但不能省掉当前阶段的门槛与证据：

```text
- run_id：
- 模式 / 当前模式：
- 状态：
- 当前门槛 / 最早门槛：
- 当前价值缺口 / 当前最大缺口：
- 下一技能：
- 证据状态：
- 当前 Q：
- 当前 D：
- 已记录决策：
- 产物清单 / 已保存资产：
- 建议下一步：
```

证据状态至少说明：

- 产品简报：未创建 / 草稿 / 待确认 / 已对齐 / 有漂移。
- Zoon：无 URL / 已同步 / 有漂移 / 读取失败 / 未启用。
- 线上参考：已提供线上参考 / 无线上参考已确认 / 缺失待补充 / 不适用。
- 原型清单：未生成 / 已登记 / 已生成 / 已复审 / 需重出。
- 用户全局记忆：暂无 / 已读取 / 已应用并明示来源 / 有 GitHub 回流待审稿。
- 待决策项：无 / 当前 Q / 当前 D / 后续 D 队列。
- 不可虚构项：未定义 / 已定义 / 有违规。
- 交付资产：未生成 / 已保存 handoff / 不适用。

## 状态值地图

统一状态来自 `runtime-kernel.md`，各阶段可以在行动结论里使用更细状态：

- `需要补充`：缺少会改变方向或交付质量的事实、参考或证据。
- `待确认`：已有假设、前提或推荐，需要用户确认。
- `需要 PM 拍板`：存在会改变承诺、范围、数据真实性、实验口径、线索/交易/隐私/合规或验收的取舍。
- `基于假设，可讨论`：快速成型轻量包可讨论，但不是最终 PRD 或已验证事实。
- `已对齐`：产品简报、关键前提或最新 Zoon 已确认。
- `可进入原型复审`：已生成独立原型图片，需要复审。
- `需要补充参考`：缺少线上截图、设计系统、输出单元绑定或真实数据边界。
- `需要重出`：图片违反 brief、反指标、不可虚构项、线上参考或设计系统。
- `可通过`：原型复审通过，可进入交付。
- `可交付`：交付前门槛全部通过，交付稿可以保存并交给下一团队。

## Eval 分类地图

`pmw-eval` 的 fixture `category` 必须能映射回链路阶段：

| Eval 分类 | 对应阶段 | 主要守住什么 |
|---|---|---|
| `pm-workspace-entry`、`pm-workspace-routing`、`pm-workspace-runtime` | 欢迎与 D0 路由 | 欢迎页、D0、路由输出契约、run owner |
| `autoplan`、`quick-shaping`、`deep-delivery` | 自动产品评审 | 自动推进、风险升级、最早门槛、终态 finish |
| `pm-jobs` | 产品价值澄清 | 价值澄清器、价值判断先行、一个 Q / D、前提确认、上游门槛接力 |
| `pm-strategy-review` | 策略审查 | 策略结论先行、最大策略矛盾、产品动作、缺事实退回、一个策略 D |
| `pm-brief` | 产品简报 | 核心信息契约、核心信息先行、支持信息分层、Zoon 漂移、已对齐门槛、进入原型/交付 |
| `pm-prototype-shotgun`、`prototype-shotgun`、`prototype-output-contract`、`multi-scheme`、`production-reference`、`screenshot-feedback` | 原型方案 | image-2 前门槛、单图生成协议、方案差异质量、输出单元、线上参考、设计系统 |
| `prototype-review` | 原型复审 | 复审控制器、重出、PM 拍板、偏好边界 |
| `pm-handoff` | 产品交付 | 未复审不交付、未拍板不写验收、保存 handoff |
| `memory`、`decision-principles`、`eval-system` | 运行与记忆 | 偏好不覆盖事实、eval runner 可用、维护契约 |

新增 fixture 时，先把它放入上表已有分类；如果确实出现新阶段，必须同步更新本文件、`pm-eval-system.md` 和 `evals/README.md`。

## 链路收口规则

- README 只讲产品体验和入口，不维护第二套路由表；它应链接或摘录本地图。
- `routing.md` 只决定下一技能和 D0，不重复展开每个技能的完整 controller。
- `pm-eval-system.md` 只维护测试分层、fixture 结构和分类地图，不复制技能全文。
- 技能 `SKILL.md` 必须读取本文件，并在输出中保留本阶段要求的状态字段。
- 如果某个门槛失败，下一技能必须指向最早能补齐该门槛的技能；不要把下游产物伪装成已完成。
