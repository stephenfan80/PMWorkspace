# PMWorkspace 路由

决定下一步由哪个 PMWorkspace 专家负责时使用本文件。PMWorkspace 的主定位是产品专家增强器：路由不是把用户送进更长流程，而是把用户送到最能增强当前产品判断力的专家能力。

For Chinese users, use Chinese names in explanations and keep skill ids unchanged.

## 主入口协议

`$pm-workspace` 只读取本文件作为路由唯一真源；不要在 `$pm-workspace/SKILL.md` 里维护第二份路由表。

`$pm-workspace/SKILL.md` 只保留入口职责、平台 preamble、controller 衔接和工作方式卡片字段；产品发现、线上参考、原型、复审、交付、Zoon 和产物流动细则必须留在共享 reference 或对应子 skill，不回填到入口文件。

PMWorkspace 对用户只暴露四个动作：`对齐`、`出图`、`复审`、`交付`。路由表可以映射到底层 skill，但默认用户输出先说明当前动作和价值，不先抛出 8 个 skill 名称。四个动作的含义：

| 用户动作 | 用户想完成的事 | PMW 默认处理 |
|---|---|---|
| 对齐 | 把想法、PRD、截图、反馈或数据变成可讨论产品判断。 | 判断全新功能 / 已有功能迭代，补齐真实问题、当前替代、目标、反指标和产品简报。 |
| 出图 | 基于已对齐 brief 生成 image-2 原型图。 | 先跑 Product Readiness Dashboard，再逐个方案 / 屏幕单独出图。 |
| 复审 | 判断原型图是否可通过、重出、补参考或拍板。 | 检查 brief、线上参考、不可虚构项、设计系统和数据可行性。 |
| 交付 | 把确认方向转成 PRD、产品设计文档或研发交付。 | 先确认复审和交付门槛，再整理精简 PRD / handoff。 |

路由前同时读取 `pm-workbench-map.md`。本文件决定“下一技能是什么”，`pm-workbench-map.md` 决定“当前链路阶段、共享状态字段和 eval 分类怎么对齐”。

路由前先建立 `产品信息对齐包`。脚本可用时，先运行 `pmw-controller intake` 生成或继承本轮 run / `task_digest` / `input_revision`，再读取 `pmw-dashboard status` 默认摘要；脚本不可用时，也要用当前对话、已对齐 brief、截图、Zoon、artifact-flow 和 run 事实手动整理同样字段。路由不能只看用户最后一句“要原型 / 使用方案 A / 参考截图”，必须先判断当前事实是否足以继续下游。

路由前先运行 `pmw-trigger-guard --text "<本轮用户原话和材料摘要>" --skill pm-workspace --json`。只要返回 `pmw_required=true`，就不能退回普通 Agent 行为；如果 PMW runtime 或专用动作不可用，必须停止并说明 `PMW runtime 未接管当前任务，已阻断普通方案输出和出图`。禁止说“插件触发到了但没有直接暴露 pmworkspace 动作，所以我继续用本地数据做方案”；这类 fallback 会绕过工作方式卡片、自动产品评审、产品方向审查、brief 确认、设计规范 D、readiness 和 image permit。

`pmw-controller next` 是路由后的唯一合法下一动作来源。返回 `ASK_CONFIRMATION`、`NEEDS_BASELINE`、`WRITE_PENDING_BRIEF`、`BRIEF_PENDING`、`D_REQUIRED` 或 `BLOCKED` 时，路由必须停在当前门槛；不要因为历史资料充足、旧 brief 已对齐或旧 board 有 3 个方案就继续下游。

路由前先完成产品路径识别：`全新功能` 或 `已有功能迭代`。PMWorkspace 不再提供轻量旁路对齐深度；所有产品任务都走深度产品对齐。只有产品路径不清、风险信号冲突或输入材料不足以判断时，才停在路径/证据卡点等待用户回答。

无论自动判定还是用户选择，路由输出必须给用户一个短的工作方式卡片，避免“产品路径 / 对齐深度”只停留在内部状态：

```text
工作方式：
- 当前动作：对齐 / 出图 / 复审 / 交付
- 产品路径：全新功能 / 已有功能迭代 / 待判断
- 对齐深度：深度产品对齐（固定）
- 为什么：<一句话引用用户输入或风险信号>
- 本轮价值时刻：<本轮先帮用户获得的关键判断，例如判断是否值得做 / 找出最大损失 / 收缩到可赢切口 / 判断是否可出图>
- 产品信息对齐：<已对齐 / 缺目标用户 / 缺当前替代 / 缺真实损失 / 缺线上基线 / 缺反指标等>
- 已完成：<已整理的材料或已判定事项>
- 当前任务：<本轮处理的任务流阶段或最早门槛>
- 下一步：<下一阶段>
- Agent 可协助什么：<整理材料 / 拆截图 / 访谈提纲 / 数据口径 / 最佳实践检索 / 原型计划>
- 需要用户补什么：<回答 Q/D、确认假设、补截图、补数据或选择下一步>
- 补齐后解锁：<补完当前卡点后能进入的产物或判断，例如产品简报 / 页面输出模式 / image-2 原型计划 / PRD 交付稿>
```

如果用户明显只想先拿讨论稿，也仍然走深度产品对齐，只是可以把当前产物收敛为“待确认讨论稿”；不能因此跳过产品简报确认或出图前 readiness。

用户选择 `方案 A/B/C`、回答“按 A 继续”或确认某个方向，只代表方案方向选择，不能替代当前 `input_revision` 的产品简报对齐。

## 入口硬停规则

这些规则由 `$pm-workspace` 入口执行，但不要回填到入口 `SKILL.md` 形成第二份协议：

- 写图片提示词或生成图片前，必须先完成当前 `input_revision` 的产品简报对齐。
- 用户提供截图或线上参考时，只更新视觉基线和线上参考状态；不要自动产出完整方案、HTML 或原型图。
- 已有功能迭代缺线上截图、关键节点截图或等价视觉基线时，不输出 `方案 A / 方案 B / 方案 C`；先请求证据并解释补齐后解锁什么。
- 用户选择某个方案方向后再上传截图时，只代表“方向选择 + 新证据输入”，不代表产品简报已对齐；先进入 `线上基线接收`，再回到 `$pm-brief` 确认。
- 入口层默认只解释 5 个公开产品资产：`product_brief`、`visual_baseline`、`prototype_manifest`、`prototype_review`、`handoff`；完整 Product Artifact Flow 写入本地审计。
- 不要把真实 token、私密客户数据、内部录音、敏感截图或未脱敏 Zoon 内容保存到本地资产。

## 价值判断可感知层

路由不是把用户送到更长流程，而是让用户知道当前产品判断为什么值得做。每次进入 PMW、切换工作方式或遇到阻断门槛时，必须用一句业务语言说明：

- `当前判断是什么`：本轮先判断产品是否值得做、应该收缩到哪里、是否能出图，还是是否能交付。
- `证据边界在哪里`：当前判断基于用户输入、已对齐 brief、线上截图、数据、竞品、Zoon 或本地 run；缺什么就明说缺什么。
- `为什么当前卡点重要`：说明它影响真实问题、现状替代、当前损失、范围模式、不可虚构项、原型可信度或交付承诺中的哪一项。
- `补齐后会解锁什么`：用户补完后可以进入产品简述、页面输出模式、image-2 原型计划、原型复审或 PRD / 交付稿。

不要把“请补截图 / 请补数据 / brief 未对齐”写成纯流程阻断。必须解释它对产品价值判断的意义：例如已有功能缺线上截图，会导致 PMW 无法判断哪些结构必须保留、问题区域是否真实存在，以及原型是否可信。

## 产品路径判定与深度对齐

| 判定维度 | 全新功能信号 | 已有功能迭代信号 |
|---|---|---|
| 用户说法 | 我有一个产品想法、想做一个新能力、从 0 到 1、MVP、先验证 | 想优化 xxx 功能、现在线上页面、已有流程、截图/关键节点截图、数据下降、反馈很多 |
| 关键材料 | 目标用户、触发场景、当前替代、损失、竞品/最佳实践 | 线上截图、关键节点截图或视觉基线、当前数据/业务现状、问题区域、保留项、可改项 |
| 原型门槛 | 判断是否需要线上参考；证据不足可假设驱动 | 缺线上截图/视觉基线时阻断原型计划；缺数据时只能假设原型并标风险 |

所有产品任务固定进入深度产品对齐。`想先拿出去讨论`、`先给几个方案`、`原型图`、`PRD`、`设计评审`、`研发交付` 等输出目标只影响当前最早门槛和最终产物深浅，不再改变对齐深度。

内部判定默认：

- 用户明确给出线上页面、当前流程、生产截图、业务指标或已有反馈时，产品路径倾向 `已有功能迭代`。
- 用户明确说从 0 到 1、新能力、MVP 或没有现有线上承接流程时，产品路径倾向 `全新功能`。
- 用户同时说“新工具 / 新功能”和“提升已有业务指标 / 线上转化 / 留资 / 交易 / 线索”等信号时，不能自动拍板路径，必须先问 `D0 产品路径`。
- 对齐深度固定为 `深度产品对齐`，不再询问快慢模式。

当产品路径无法判断时，先问路径选择，而不是先问快/深：

```text
D0 产品路径
A. 全新功能：从想法、需求或 MVP 开始澄清。
B. 已有功能迭代：基于线上功能、截图、数据或反馈优化。
```

## 路由表

| 用户动作 | 用户意图 | 路由 |
|---|---|---|
| 对齐 | 想先给几个方案、自动推进、按推荐走但关键点拍板 | `$pm-autoplan` 深度产品对齐 |
| 对齐 | 原始想法、模糊请求、“帮我想想”、“是否值得做” | `$pm-jobs` 产品方向审查内核 |
| 对齐 | 一次自动跑完整产品评审、PRD、设计评审、研发交付，但上游事实未齐 | `$pm-autoplan` 深度产品对齐 |
| 对齐 | 策略、范围、野心、风险、价值交换、“想大一点” | `$pm-strategy-review` |
| 对齐 | 需要可沉淀的产品简报或 Zoon 对齐资产 | `$pm-brief` |
| 出图 | 需要 image-2 原型图、多方案、截图修改 | `$pm-prototype-shotgun`，把多方案表达成多条产品路径 |
| 复审 | 已生成原型图，需要复审、重出判断、偏好沉淀 | `$pm-prototype-review` |
| 交付 | 需要产品设计文档、PRD、设计、实验验证或研发使用的交付稿 | `$pm-handoff` |

多个路由都适用时，先判断模式，再从最早缺失的资产开始：

1. 新 idea 且用户要“先拿出去讨论” -> `$pm-autoplan`，但仍先完成深度产品对齐。
2. 产品问题不清楚 -> `$pm-jobs`。
3. 问题清楚，但策略/范围有争议 -> `$pm-strategy-review`。
4. 策略清楚，但没有已对齐的产品简报 -> `$pm-brief`。
5. 产品简报已对齐，并且用户要原型 -> `$pm-prototype-shotgun`。
6. 原型已生成，但需要验收、复审或重出判断 -> `$pm-prototype-review`。
7. 方向已选定，下一团队需要接手 -> `$pm-handoff`。

## 路由输出契约

每次 `$pm-workspace` 完成路由后，默认只给用户一个短业务摘要：

```text
工作方式：
当前动作：
本轮价值时刻：
业务判断：
当前需要确认：
补齐后解锁：
下一步：
```

完整路由字段必须写入本地审计；用户明确要求“看状态 / 看审计 / 调试 / 展开证据”时才输出：

```text
当前模式：
产品路径：
对齐深度：
当前门槛：
下一技能：
为什么：
run_id：
证据状态：
```

- `产品路径`：全新功能 / 已有功能迭代 / 待判断。
- `对齐深度`：深度产品对齐 / 维护检查。
- `当前门槛`：当前必须停住或即将处理的最早门槛，例如 D0 产品路径、产品简报未已对齐、线上参考缺失、原型复审、交付确认。
- `下一技能`：写 skill id，例如 `$pm-autoplan`。
- `为什么`：用一句话说明路由依据，只引用用户输入、已对齐产品简报、最新 Zoon、截图/线上参考或当前 run 证据，不用历史偏好替代事实。
- `run_id`：平台脚本可用时由 `pmw-controller intake` 创建或继承；脚本不可用时写 `未启用`。
- `task_revision`：平台脚本可用时记录 `task_digest` / `input_revision`；旧产物若不匹配只能写 `可参考，不可放行`。
- `证据状态`：至少说明产品简报、Zoon、线上参考、原型清单、待决策项和 Product Readiness Dashboard 的当前状态；未知项写 `未提供`、`未运行` 或 `待检查`。
- `设计规范待确认`：如果 controller 返回 `early_design_spec_decision`，工作方式卡片里先露出“本轮原型使用哪个设计规范目标”的 D。汽车之家 / AutoDesign / 独号 / 线索 / 询价 / 查价 / 经销商 / 新能源车系页等信号默认推荐汽车之家 AutoDesign；这个 D 可以先露出，不阻断产品方向审查，但会阻断出图。

## Run 衔接

`$pm-workspace` 是路由型会话的 run owner：完成 D0 和路由判定后先调用 `pmw-controller intake`，由 controller 判断是否复用当前 active run、创建新 revision 或新 run，并记录当前门槛、证据状态和下一技能。被路由到的子 skill 必须复用当前 controller run/revision；只有用户直接调用子 skill 且没有当前 run 时，子 skill 才通过 controller 创建自己的 run。全局 `current-project` 只是候选上下文，不能跳过 controller 的语义匹配。

## 端到端地图衔接

路由结果必须落在 `pm-workbench-map.md` 的一个链路阶段上：

- 欢迎与产品路径路由 -> `$pm-workspace`
- 自动产品评审 -> `$pm-autoplan`
- 产品追问 -> `$pm-jobs`
- 策略审查 -> `$pm-strategy-review`
- 产品简报 -> `$pm-brief`
- 原型方案 -> `$pm-prototype-shotgun`
- 原型复审 -> `$pm-prototype-review`
- 产品交付 -> `$pm-handoff`

如果某个门槛失败，下一技能必须指向最早能补齐该门槛的阶段；不要跳到下游产物。

## 统一深度产品对齐工作流

```text
pm-workspace
-> pm-jobs
-> pm-strategy-review when strategy risk is material
-> decision questions when PM tradeoffs remain
-> pm-brief + Zoon online doc
-> pm-prototype-shotgun reads latest Zoon brief
-> pm-prototype-review checks generated images
-> pm-handoff
```

生成图片前，不能跳过已对齐的产品简报。用户只说“先给几个方案”“选 A”“按 A 继续”都只能推进到产品简报或方案方向确认，不能触发 image-2。
