# PMWorkspace Eval 体系

PMWorkspace eval 第一版用于维护技能规则和输出契约，不运行真实 image-2，不做美感判断，也不调用 LLM-as-judge。它验证的是：核心门槛有没有被文档和 skill 保住。

第一版只测规则和输出契约，不跑真实 image-2，也不做美感判断。

## 目标

- 防止深度交付未对齐时写 image-2 提示词或生成原型。
- 防止快速成型未确认假设时进入图片生成。
- 防止现有功能迭代缺线上截图仍越过参考门槛。
- 防止多方案只换配色、圆角或插画。
- 防止历史偏好覆盖当前 brief、Zoon、反指标或不可虚构项。
- 防止原型复审接受“好看但误导”的图片。
- 防止 PM Review Army 退化为一段泛泛总评：策略、信任 / 风险、设计系统、数据可行性必须作为可插拔专家独立输出短结论，再由原型复审合并。
- 防止用户反馈资产混淆：个人偏好、产品认知和 PMWorkspace 进化建议必须分开保存，GitHub 回流默认只生成脱敏本地待审稿。
- 防止 PMWorkspace 主入口路由分散、run 重复创建或路由输出缺少证据状态。
- 防止产品交付退化成大而全 PRD：默认只输出精简 PRD 核心字段，接口、数据、埋点和实验缺口可留空但不能虚构，并沉淀为本地交付资产。
- 防止出图 / 交付前缺少统一准备度判断：Product Readiness Dashboard 必须展示 brief、Zoon、线上参考、方案差异、不可虚构项和复审状态，并给出 verdict。
- 防止下游技能重新猜上游事实：Product Artifact Flow 必须把产品简报、原型清单、复审结论和交付稿登记为下游可读产物。
- 防止线上证据采集变重或断流：浏览器证据必须以 `browser_evidence` 产物流入 Product Artifact Flow，并被 Product Readiness Dashboard 的线上参考行优先读取。
- 防止 SKILL.md 手写漂移：`pmw-gen-skill-docs` 必须从 manifest 生成并检查共享 preamble、必读协议、输出字段和共享门槛。

## 分层

- **协议静态检查：** 检查 fixture 指向的 skill 和 reference 是否仍包含关键规则。
- **场景契约检查：** 检查每个 fixture 是否声明输入、预期状态、停止门槛、禁止行为和必须行为。
- **运行时契约检查：** 检查 `pmw-run`、`pmw-dashboard`、`pmw-prototype-board`、`pmw-memory` 等脚本是否仍提供需要的记录入口。
- **产物流动契约检查：** 检查 `pmw-artifact`、`artifact-flow.jsonl`、`browser_evidence`、技能读取协议和 dashboard 展示仍能支持下游接力。
- **复审专家契约检查：** 检查 `pmw-review-specialist`、四个默认专家、专家短结论结构和 `$pm-prototype-review` 合并协议。
- **Skill 文档生成检查：** 检查 `pmw-gen-skill-docs`、manifest、生成契约区块和共享字段防漂移规则。
- **端到端地图检查：** 检查 README、`routing.md`、skill 状态字段和 eval 分类仍能映射到 `pm-workbench-map.md`。

第一阶段仍只做静态规则和场景契约检查；运行时契约和端到端地图检查都通过 fixture 的 `contract_checks` 引用脚本或文档关键短语。

## Eval 分类地图

fixture 的 `category` 必须能映射回 `pm-workbench-map.md` 的链路阶段。新增分类前，先更新 `pm-workbench-map.md`、本节和 `evals/README.md`。

| 分类 | 链路阶段 | 代表 fixture |
|---|---|---|
| `pm-workspace-entry`、`pm-workspace-routing`、`pm-workspace-runtime` | 欢迎与 D0 路由 | 欢迎页、D0、路由输出、run 复用 |
| `autoplan`、`quick-shaping`、`deep-delivery` | 自动产品评审 | 自动推进、快速成型确认、深度交付门槛 |
| `pm-jobs` | 产品价值澄清 | 价值澄清器、价值判断先行、一个 Q / D、前提确认 |
| `pm-strategy-review` | 策略审查 | 策略取舍裁判、范围模式、最大策略矛盾、产品动作、策略 D |
| `pm-brief` | 产品简报 | 核心信息契约、核心信息先行、支持信息分层、Zoon 漂移、已对齐门槛 |
| `pm-prototype-shotgun`、`prototype-shotgun`、`prototype-output-contract`、`multi-scheme`、`production-reference`、`screenshot-feedback` | 原型方案 | image-2 前门槛、单图协议、输出单元、线上参考、设计系统 |
| `prototype-review` | 原型复审 | 复审控制器、重出、拍板、偏好边界 |
| `review-specialists` | 原型复审 | 可插拔专家、短结论、最高严重度合并、dashboard 专家汇总 |
| `pm-handoff` | 产品交付 | 精简 PRD、现成文档入口、未复审不交付、未拍板不写验收、交付资产沉淀 |
| `readiness-dashboard` | 原型方案 / 产品交付 / 运行与记忆 | 出图 / 交付前 Product Readiness Dashboard 和 verdict |
| `artifact-flow` | 产品简报 / 原型方案 / 原型复审 / 产品交付 / 运行与记忆 | Product Artifact Flow、`pmw-artifact`、`browser_evidence`、上游产物下游可读 |
| `skill-doc-generator` | 运行与记忆 | `pmw-gen-skill-docs`、manifest、生成契约区块、共享字段防漂移 |
| `memory`、`decision-principles`、`eval-system` | 运行与记忆 | 偏好边界、个人全局记忆、GitHub 待审稿、自动决策、eval runner |

## Fixture 结构

fixture 使用 JSON，保存在 `evals/fixtures/`：

```json
{
  "id": "quick-assumption-confirmation-required",
  "title": "快速成型出图前必须确认假设",
  "category": "quick-shaping",
  "primary_skill": "pm-autoplan",
  "prompt": "用户请求示例",
  "expected": {
    "mode": "quick",
    "status": "待确认",
    "must_stop": true,
    "gate": "假设确认",
    "required_behaviors": ["列出关键假设", "等待用户确认"],
    "forbidden_behaviors": ["生成 image-2 图片", "写成最终 PRD"]
  },
  "contract_checks": [
    {
      "path": "pm-autoplan/SKILL.md",
      "contains": "确认前不生成图片"
    }
  ]
}
```

## 断言类型

`pmw-eval` 第一版支持：

- `contains`：指定文件必须包含某个关键短语。
- `contains_any`：指定文件必须包含候选短语中的至少一个。
- `not_contains`：指定文件不得包含某个短语；谨慎使用，只用于防止明确错误协议。

断言面向规则文档和 skill 文本，不面向模型输出。这样能在不花费 API 成本的情况下，先守住 PMWorkspace 的制度性门槛。

## 必测场景

- 端到端地图：README、routing、eval 分类和 skill 状态字段必须共同指向 `pm-workbench-map.md`，不能各自维护一套链路解释。
- Skill 文档生成：共享 preamble、必读协议、输出字段和共享门槛必须进入 `skill-docs.manifest.json`，由 `pmw-gen-skill-docs write` 生成，且 `pmw-gen-skill-docs check` 能发现漂移。
- 深度交付：产品简报未 `已对齐` 时禁止 image-2 提示词和图片生成。
- 快速成型：未确认“按这些假设继续”前禁止生成图片。
- 现有功能迭代：缺生产截图或录屏时必须停在参考门槛。
- 新页面承接线上流程：缺上一步、相似结果页或状态页参考时必须停下。
- 截图反馈：用户只提供截图时，只更新视觉基线，不自动产出完整方案或原型图。
- 多方案：方案差异必须来自页面结构、信息架构、交互路径、信任表达或关键任务。
- 输出单元：每张图必须绑定方案名、屏幕任务、主目标、反指标、不可虚构项、产品简报版本、线上参考状态、设计系统和 image-2 状态。
- 记忆：拒绝过的方向不能作为新方案推荐；应用偏好时必须明示来源。
- 原型复审：违反 brief、反指标、不可虚构项、线上参考或设计系统时，必须标为 `需要重出` 或 `需要 PM 拍板`。
- 反馈资产化：原型复审必须输出 `反馈资产化`，并区分可沉淀为个人偏好、可沉淀为产品认知、可回流 PMWorkspace、不应保存和已保存到。
- 用户记忆：反馈资产必须支持个人全局 + 项目局部；全局资产保存在 `~/.pmworkspace/user/` 等价目录，项目资产保存在 `projects/<slug>/`。
- 用户记忆：历史偏好和产品认知不能覆盖当前 brief、Zoon、反指标、不可虚构项或线上参考门槛；应用时必须明示来源和适用范围。
- 用户记忆：产品认知不能混写成普通审美偏好；事实错误、反指标风险、不可虚构违规、线上参考缺失或未决承诺不能保存为普通 taste。
- GitHub 回流：默认只能生成脱敏本地待审稿，不自动提交 GitHub、issue 或 PR；草稿不得包含真实项目名、Zoon 正文、截图内容、客户信息、token、内部 URL 或未脱敏 PRD。
- PMWorkspace 主入口：空泛请求展示产品首页式欢迎；明确任务直接路由，不要求用户猜命令。
- PMWorkspace 主入口：D0 工作方式必须覆盖输出目标、输入材料、风险等级、是否生产流程、是否要交付。
- PMWorkspace 主入口：每次路由后必须输出 `当前模式`、`当前门槛`、`下一技能`、`为什么`、`run_id`、`证据状态`。
- PMWorkspace run：主入口创建 run；子 skill 复用当前 run，只有直接调用且没有当前 run 时才创建 run。
- 自动产品评审：必须先建立控制面板，输出模式来源、推进阶段、最早门槛、停止原因、下一技能和证据状态。
- 自动产品评审：必须定义“靠谱产品负责人”，默认采用平衡总控姿态，事实优先、结论明确、自动但不越权、最早门槛优先且交接负责。
- 自动产品评审：用户可见输出必须结论先行，先输出 `自动评审结论`、`我建议` 和 `理由`，再输出评审控制面板。
- 自动产品评审：最早门槛必须标注 `门槛等级` 和 `门槛来源`，等级只使用阻断、高风险、可自动采用或可延后。
- 自动产品评审：每个自动采用项必须说明来源和不需要 PM 拍板的理由；不能把无来源判断、承诺口径或数据真实性自动采用。
- 自动产品评审：下一技能不能只写 skill id，必须输出包含来源门槛、已确认事实、未决 Q/D、证据状态和交给它的原因的交接上下文。
- 自动产品评审：快速成型输入出现生产流程、高风险承诺、真实数据、线索/交易/隐私或研发交付信号时，必须升级到深度交付门槛。
- 自动产品评审：深度交付每轮只推进到最早仍不可靠的门槛，并映射到一个下一技能，不能假装完整下游流程都已完成。
- 产品追问：必须定义“产品价值澄清器”，默认采用平衡型姿态，先重新定义真实问题并逼近真实需求，也保留产品简报、原型和交付门槛。
- 产品追问：必须区分问题定义模式：创业验证、内部业务优化或设计讨论；模式会影响真实问题重定义、当前最大缺口和下一问。
- 产品追问：用户可见输出必须价值判断先行，先输出 `产品价值判断`、`我对真实问题的判断`、`我现在判断`、`当前价值缺口`、`为什么这是最该问的一刀` 和 `这个答案会影响`，再输出追问控制面板。
- 产品追问：每轮必须输出一句 `我对真实问题的判断`，把功能愿望重写成用户问题、当前损失或决策任务；事实不足时写成暂定判断并用当前 Q 验证。
- 产品追问：不能把功能愿望直接当成核心问题；用户只给功能名、AI 能力或页面想法时，必须追问真实用户、触发场景、当前损失或现状替代。
- 产品追问：进入方案方向、前提确认或产品简报前，必须识别现状替代方案和最小可赢切口；价值仍宽泛时，不能直接写完整产品简报。
- 产品追问：每个用户可见 `Q` / `D` 必须说明为什么现在问和这个答案会影响什么。
- 产品追问：必须先建立产品价值澄清控制器，输出诊断阶段、当前价值缺口、当前最大缺口、Q 预算、停止原因、下一技能和证据状态。
- 产品追问：每轮只能展开一个 `Q` 或一个 `D`；缺事实先问 Q，事实足够但取舍改变方向时才问 D。
- 产品追问：来自 `$pm-autoplan` 时，只解决自动评审交给 `$pm-jobs` 的最早门槛，不能假装下游产品简报、原型或交付已完成。
- 策略审查：必须定义“策略取舍裁判”，不替代 `$pm-jobs` 补事实，不替代 `$pm-brief` 写产品契约。
- 策略审查：必须显式选择范围模式：扩大模式、保持模式、收缩模式或转向模式；范围模式必须说明如何处理范围、价值交换、反指标和不可虚构边界。
- 策略审查：用户可见输出必须结论先行，先输出 `策略审查结论`、`我建议`、`最大策略矛盾`、`范围模式`、`建议姿态`、`为什么`、`当前必须拍板` 和 `进入产品简报的写法`，再输出策略取舍控制面板。
- 策略审查：必须接住产品追问交出的范围、价值交换、信任/风险、反指标、可行性、定位或业务冲突门槛，并输出来源门槛、策略风险类型、使用视角、最大策略矛盾、范围模式、产品动作、策略取舍、当前 D、下一技能和证据状态。
- 策略审查：缺少用户、问题、主目标、反指标或不可虚构项等基础事实时，必须退回 `$pm-jobs` 问一个 `Q`，不能用策略审查虚构事实。
- 策略审查：事实足够但不同选择会改变范围、价值交换、用户承诺、实验口径、信任风险、可行性边界或交付责任时，只展开一个完整 `D` 并停止。
- 策略审查：每个审查视角必须转成产品动作：删除、前置、后置、标注、禁止或实验验证；不能只列风险。
- 策略审查：策略 `D` 必须说明推荐项、风险、会影响什么，以及进入产品简报的写法。
- 策略审查：交给 `$pm-brief` 时必须带范围模式、策略决策、最大策略矛盾、范围外、用户承诺边界、反指标保护和对原型的影响。
- 产品简报：必须定义“产品核心信息契约”，说明产品简报不是 PRD、会议纪要或信息仓库，只压缩会影响原型、复审或交付的判断。
- 产品简报：用户可见输出必须核心信息先行，先输出 `产品核心信息`，再输出 `产品简报门槛`，最后输出 `支持信息`，不能先给长状态表。
- 产品简报：`产品核心信息` 必须包含目标用户 / 场景、核心问题 / 当前损失、当前替代方案、本次目标、反指标、策略选择、原型重点和不可虚构项。
- 产品简报：Zoon、线上参考、检索来源和已保存资产必须放入 `产品简报门槛` 或 `支持信息`，不能挤占核心信息。
- 产品简报：互联网案例启发只能压缩为可借鉴原则、不可照搬和对原型影响；最佳实践不能覆盖当前 brief、Zoon、线上截图、反指标或不可虚构项。
- 产品简报：简报深度不等于内容长度；快速版、标准版、深度版都必须保持同一套精简核心信息，深度只影响支持信息中的证据、边界和决策记录。
- 产品简报：必须先建立产品简报契约控制器，并输出来源门槛、简报深度、缺失门槛、事实/假设边界、策略决策写入、下一技能和证据状态。
- 产品简报：来自 `$pm-jobs` 或 `$pm-strategy-review` 的基础事实、风险、范围或价值交换门槛未解决时，必须退回对应技能，只展开一个当前 `Q` 或 `D`，不能写成已对齐产品契约。
- 产品简报：策略审查完成后，必须把范围模式和策略取舍写入对抗审查后的设计取舍、方案方向、范围外、决策记录和对原型的影响。
- 产品简报：`pmw-log brief` 必须使用 Zoon-first，local-backed 同步；先推送或追加 Zoon，成功后再保存同一份本地审计副本，并记录 Zoon URL、同步状态和最终本地 brief 路径。
- 产品简报：Zoon 漂移如果改变目标、反指标、不可虚构项、范围、用户承诺或方案方向，必须重新确认，不能继续沿用旧的已对齐状态。
- 产品简报：只有确认状态已对齐、线上参考门槛通过且无未解决缺失门槛时，才能把下一技能指向 `$pm-prototype-shotgun` 或 `$pm-handoff`。
- 产品准备度仪表盘：出图 / 交付前必须输出 Product Readiness Dashboard，至少覆盖产品简报、Zoon、线上参考、方案差异、不可虚构项和复审状态，并给出 `可出图`、`不可出图`、`可交付` 或 `不可交付` verdict。
- 产物流动：下游技能必须读取 Product Artifact Flow；`pmw-log brief`、`pmw-log prototype`、`pmw-log handoff` 必须把 product_brief、prototype_manifest 和 handoff 登记为下游可读产物。
- 浏览器证据：线上截图、状态页、竞品参考或 Zoon 漂移证据必须登记为 `browser_evidence` 产物；`pmw-dashboard readiness` 的线上参考行优先读取它，没有时才回退 run evidence / gate 事件。
- 原型方案：必须定义 `$pm-prototype-shotgun` 是 image-2 原型出图导演；它不重新做 `$pm-jobs`、`$pm-strategy-review` 或 `$pm-brief` 的职责。
- 原型方案：必须先输出 `原型出图判断`，再进入方案方向、图片输出单元和 prompt；不能直接写 image-2 prompt。
- 原型方案：必须先建立原型方案控制器，并输出产品简报来源、图片生成前门槛、方案差异质量、方案方向确认、输出单元清单、方案比较板写入和证据状态。
- 原型方案：产品简报缺失、未已对齐、Zoon 有实质漂移或线上参考缺失时，必须退回对应门槛，不能写 image-2 提示词或生成图片。
- 原型方案：多方案差异必须先通过页面结构、信息架构、交互路径、信任表达或关键任务检查；不允许把配色、圆角、插画、卡片样式或视觉皮肤包装成方案。
- 原型方案：方案质量规则不局限留资业务；社区、直播、产品库、交易、内容、工具、看板等场景也必须适用。
- 原型方案：每个 `方案 + 屏幕任务` 必须是一张独立图片，且生成前用 `pmw-prototype-board add` 登记，生成后用 `pmw-prototype-board image` 补充图片路径或 URL。
- 原型方案：一次 image-2 调用只能对应一张图、一个方案和一个屏幕任务；`3 个方案` 必须拆成 3 个输出单元，不能生成一张三联图。
- 原型方案：image-2 prompt 必须禁止拼图、三联图、并排比较、一图多屏、一图多方案和故事板。
- 原型方案：输出单元：每张图必须绑定方案名、屏幕任务、主目标、反指标、不可虚构项、产品简报版本、线上参考状态、设计系统和 image-2 状态。
- 原型方案：汽车之家场景必须加载 AutoDesign 约束，产品 UI 优先使用 AutoDesign token。
- 原型方案：品牌 VI 和字体包只作为品牌露出、活动视觉或特殊场景参考；不能覆盖 AutoDesign 产品 UI token，也不能写成字体已授权可生产。
- 原型方案：image-2 不可用时必须停止说明，不能用 HTML、Markdown 线框、拼贴图或方案比较板替代原型图。
- 原型复审：必须先建立原型复审控制器，并输出复审输入、输出单元绑定、复审视角、判定原因、行动结论、修正方向、PM 拍板、偏好沉淀和证据状态。
- 原型复审：PM Review Army 必须先运行四个可插拔专家：策略、信任 / 风险、设计系统、数据可行性；每个专家独立输出短结论、最高严重度、证据、一句话判断和行动，再由原型复审合并。
- 原型复审：深度交付、高风险、批量交付、研发交付、生产流程或用户要求多角色 review 时，必须输出 Product Review Squad：CEO、Eng、Design、DX、安全、QA、发布工程师七个角色短结论，再合并成行动结论。
- 原型复审：每张图片必须能追溯到一个 `方案 + 屏幕任务`、主目标、反指标、不可虚构项和产品简报版本；缺绑定时标记 `需要补充参考`，不能凭视觉印象通过。
- 原型复审：违反产品简报、反指标、不可虚构项、线上参考或设计系统时，必须标为 `需要重出`，并只为受影响屏幕输出修复 brief。
- 原型复审：用户承诺、数据真实性、范围、实验口径、线索/交易/隐私/合规边界未决时，必须标为 `需要 PM 拍板` 并输出一个当前 `D`，不能靠改图解决。
- 原型复审：偏好沉淀只能记录用户反馈或复审确认的审美/结构偏好；事实错误、反指标风险、不可虚构违规、线上参考缺失或未决承诺不能保存成普通 taste。
- 原型复审：反馈资产化是复审后的增益步骤，不能替代 `需要重出`、`需要 PM 拍板` 或 `需要补充参考`。
- 产品交付：必须先建立交付控制器，并输出交付目标、事实来源、交付前门槛、原型复审状态、未决拍板、交付类型、验收写入边界、下一技能和证据状态。
- 产品交付：产品简报未已对齐、Zoon 有实质漂移、原型复审未通过或线上参考缺失时，必须退回对应门槛，不能输出 PRD、设计交付、实验方案或研发验收。
- 产品交付：Product Readiness Dashboard verdict 不是 `可交付` 时，必须退回仪表盘第一条阻断门槛，不能输出 PRD、设计交付、实验方案或研发验收。
- 产品交付：关键 D 未拍板时，必须停止在 `需要 PM 拍板`，只展开一个当前 `D`，不能写研发验收标准、实验口径或对外承诺。
- 产品交付：验收标准只能来自已确认范围、已支持能力、已拍板承诺、已通过复审的原型或明确线上参考；不可虚构项、未验证数据和未来方案不能写成验收。
- 产品交付：默认 PRD 必须精简，只保留需求背景、需求价值、需求方案、需求功能及描述、接口以及数据来源、埋点信息、实验标准、待补充项和不可虚构；测试计划、开发周期、排期和人力默认不写。
- 产品交付：用户要 PRD、接口、埋点或实验梳理时，必须提示可上传现成 PRD、接口文档、埋点方案、实验方案、Zoon 或截图作为参考；没有文档也可基于已对齐 brief 生成精简 PRD。
- 产品交付：缺接口、数据字段、埋点属性或实验细节但不改变承诺时，必须留空或写 `待补充`，不能虚构字段、口径、事件名、接口可用性或实验阈值。
- 产品交付：用户输入中的接口、数据来源、指标口径、埋点事件、实验标准和数据可用性判断必须作为脱敏交付事实写入本地资产；使用时必须明示 `基于本地交付资产` 且不能覆盖当前 brief、Zoon、本轮输入、反指标或不可虚构项。
- 产品交付：交付稿完成时必须保存为 handoff 资产，并记录 artifact；只有交付前门槛全部通过时才能 finish run 为 `可交付`。

## 运行方式

```bash
bin/pmw-eval list
bin/pmw-eval run
bin/pmw-eval run --fixture quick-assumption-confirmation-required
bin/pmw-eval run --json
```

`list` 默认输出 fixture 数量和分类摘要；`--json` 输出机器可读结果。eval 失败时返回非零退出码。

## 维护规则

- 新增或修改 PMWorkspace 门槛时，必须补一个 fixture。
- 如果 skill 文档删掉关键短语，必须同步更新 fixture，不要只让 eval 通过。
- fixture 里不要放真实客户资料、敏感截图、token、Zoon ownerSecret 或私密 PRD 原文。
- eval 是维护工具，不是普通用户主入口；用户使用 PMWorkspace 时不需要先跑 eval。
