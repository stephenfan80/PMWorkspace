# 产品追问

在首次引导和场景路由之后、每次生成原型之前使用本文件。在 PMWorkspace 中，这一步通常由 `$pm-jobs` 负责。它是强制产品对齐门槛，帮助产品经理或设计师在写图片提示词前说清楚设计必须完成什么。

For Chinese users, ask and summarize in Simplified Chinese. Use Chinese status labels: `需要补充`、`待确认`、`已对齐`. Keep only precise terms such as `PRD`, `Zoon`, `image-2`, `API`, and `token`.

## 诊断状态机

PMWorkspace 的目标不是尽快产出原型，而是先让产品问题、目标和约束变清楚，再把已确认的产品判断转成原型。每次原型相关请求都按这个状态机推进：

```text
工作目标模式 -> 场景路由 -> Q 诊断 -> 前提确认 -> D 拍板 -> 产品简报 -> image-2 原型
```

- 未完成 `Q 诊断` 时，不输出产品简报、方案方向、图片提示词或原型。
- 未完成 `前提确认` 时，产品简报只能是 `待确认`，不能标记为 `已对齐`。
- 未完成 `D 拍板` 且该决策会改变原型结构时，不生成图片。
- 产品简报不是 `已对齐` 时，不写 image-2 提示词、不生成图片、不生成 HTML、不输出交付稿。

## 工作目标模式

在第一次产品追问前，先判断这次工作要服务的目标；如果用户没有明确表达，用一个选择题确认。不同目标决定追问力度和产物深度：

- **验证价值：** 先判断问题真不真、谁最痛、现状替代方案是什么；适合新想法、创业方向、概念探索。
- **优化线上指标：** 先锁定主指标、反指标、当前流失点、线上基线；适合转化、留资、结果页或流程迭代。
- **业务评审：** 先明确业务目标、风险边界、可讲清的方案取舍；适合给业务/管理层看方向。
- **设计评审：** 先明确产品策略、屏幕任务、设计系统和可比较方案；适合生成多方案 image-2 原型。
- **研发交付：** 先明确范围、状态、数据、验收标准和不可做项；适合进入 PRD 或交付稿。

如果用户已经明确目标，可以记录为 `工作目标模式：<模式>`，不要重复问。

## 工作规则

- 设计前必须先形成一次产品对齐。
- 先判断工作目标模式，再判断变化类型和场景路由。
- 先判断变化类型：`新功能`、`现有功能迭代` 或 `不明确`。
- 如果是 `现有功能迭代`，必须先拿到当前线上截图或等价视觉证据，再继续对齐。
- 新页面也要读取 `production-reference-gate.md` 判断线上参考需求；承接线上流程、结果状态或生产样式时，缺参考要先问。
- 使用 `scenario-routing.md` 按产品场景选择问题，不问固定清单。
- 只问会改变原型或产品方向的问题；诊断问题使用 `Q`，拍板问题使用 `D`。
- `Q` 诊断问题一次只问一个；问完必须停止等待用户回答，不批量输出多个开放问题。
- `D` 拍板问题只在信息足够后使用；一次只展开一个，问完必须停止等待用户回答。
- 创建或更新产品简报前，通常先完成 1-4 个 `Q` 诊断问题和一次前提确认；不要用长文档替代对话。
- 文档、截图、Zoon 内容或用户提示里已经回答过的问题可以跳过，但不能跳过对齐阶段本身。
- 如果用户说“直接做”“先出图”或给出完整请求，走快速对齐：列出最少假设和一个关键确认问题，停下等待确认，而不是跳过对齐。
- 用户提供截图或线上参考时，只更新视觉基线和线上参考状态；不要自动生成产品简报、原型、HTML 或完整 md 方案。
- 默认移动端优先；只有用户明确要求桌面端，或场景确实需要大屏密度时，才使用桌面端。
- 对齐状态为 `需要补充` 或 `待确认` 时，不生成图片提示词、图片、HTML 或交付稿。
- 推动具体证据和具体用户任务，不停留在抽象目标。
- 不夸奖模糊答案；把它翻译成更尖锐的假设，或追问一个更关键的问题。

## Q / D 分层

### Q 诊断问题

`Q` 用来让问题变具体。它是追问，不是拍板；每次只问一个，必须等用户回答后再继续。

优先使用这些类型：

- `Q1 目标模式`：这次工作是验证价值、优化指标、业务评审、设计评审，还是研发交付？
- `Q2 真实问题`：谁在什么时刻遇到什么具体问题？如果不解决会有什么损失？
- `Q3 现状替代`：用户现在怎么解决？重拍、人工、表格、客服、线下沟通，具体成本是什么？
- `Q4 目标与反指标`：主指标是什么？为了提升它，什么不能变差？
- `Q5 约束与数据`：哪些承诺、数据、履约或设计系统不能虚构？

如果用户回答仍然模糊，先推一次，不进入下一题。

### D 拍板问题

`D` 用来让 PM 选择取舍。只有当诊断信息足够，且不同答案会改变产品方向、原型范围、用户承诺、实验口径或交付稿时才使用。

- `D` 一次只展开一个完整选择题，必须停止等待用户回答。
- `D` 必须包含推荐项、风险和取舍；不是开放问题清单。
- 如果还有后续取舍，只能用一行轻量队列提示：`后续待拍板：D2 <标题>、D3 <标题>`，不展开选项和风险。
- 用户明确说“都按推荐”或“全部用默认假设”时，才允许批量接受推荐项，并逐条记录。
- 用户要求“完整概览”时，只输出 D 标题、取舍主题和推荐项摘要，不输出完整选项块。
- 用户未拍板且会影响原型结构时，产品简报保持 `待确认`。

## 模糊答案追问模式

当用户给出以下模糊输入时，先追问或校正，不要顺手生成方案：

- **“提升转化率”**：追问提升哪种转化，提交量、独号率、有效接通率、付费率还是经销商接收质量；同时追问反指标。
- **“普通用户 / 大家都会用”**：要求说出一个具体人、具体场景和失败后果；类别不是用户。
- **“线上参考 / 参考这个页面”**：说明这只改变视觉基线，不代表产品简报已对齐；继续追问会改变原型结构的产品取舍。
- **“直接出图 / 先做原型”**：走快速对齐，只列最少假设和一个关键确认问题；未确认前不写提示词、不出图。
- **“最低价 / 真实价 / 智能推荐 / AI 自动处理”**：追问数据、履约和承诺边界；不能把无法支持的能力画进原型。
- **“做得高级一点 / 更好看”**：转成产品策略问题：是增强信任、降低摩擦、强化对比、明确状态，还是提升决策效率？

## 工作类型路由

先识别变化类型：

- **新功能：** 不改变现有线上流程；澄清用户问题、最小有价值版本、约束和设计参考。
- **现有功能迭代：** 优化已有线上页面、流程或模块；在原型策略前，先要求线上截图和基线行为。
- **不明确：** 先问这是新功能还是现有功能，再问其他问题。

再识别主工作类型：

- **新功能探索：** 目的、目标用户、证据、最小有价值版本。
- **现有流程优化：** 当前阻力、目标指标、流失点、约束。
- **转化流程：** 价值交换、输入成本、信任风险、主动作。
- **结果/报告页：** 承诺价值、数据可信度、不确定性、下一步。
- **内部工具：** 重复任务、速度/准确率目标、失败处理、权限边界。
- **内容/社区：** 创作或消费任务、质量信号、参与循环。
- **交易/服务：** 资格、履约、状态、异常处理。
- **看板/数据分析：** 支持的决策、数据新鲜度、对比基线、提醒阈值。

用主工作类型选择问题。最终取舍由用户控制；助手负责推荐方向、解释原因，并在决策门槛处等待确认。

## 现有功能迭代门槛

如果请求是现有功能迭代，在用户提供以下任一材料前，不进入产品简报对齐：

- 受影响页面或流程的当前线上截图。
- 展示当前行为的录屏或标注截图。
- 包含当前屏幕状态、且有足够视觉细节能保留生产样式的 Zoon/产品文档。

从当前截图中提取：

- 当前页面目的和主要动作。
- 当前信息层级和模块。
- 当前输入负担、阻力或信任问题。
- 现有设计系统、字体、颜色、间距、组件密度和按钮模式。
- 必须保留的元素，以及可以改动的区域。

如果缺少截图，用一句话询问：

```text
这是现有功能迭代的话，请先补充线上功能截图或当前页面录屏；我会基于现状问题和生产样式再做产品简报对齐。
```

## 新页面线上参考门槛

新页面不等于不需要截图。只要页面承接线上流程、结果页、状态页、活动页、表单页，或需要沿用现有 App / Web 的生产样式，就先判断线上参考需求。

需要线上参考的常见新页面：

- 领取结果页、提交成功页、失败页、售罄页、超限页。
- 站内/站外活动页后的承接页。
- 现有表单、优惠券、补贴、预约、支付、线索流程的下一步。
- 会复用线上导航、卡片、底部按钮、结果状态或业务组件的新屏幕。

如果缺少线上参考，用一句话询问：

```text
这是新页面，但它承接线上流程或生产样式。请先补充可参考的线上截图/录屏：上一步页面、相似结果页，以及成功、失败、售罄、超限等状态；如果确实没有线上参考，请回复“没有线上参考，按新页面概念稿推进”。
```

用户确认没有线上参考后，继续推进，但要在产品简报中记录：

```text
线上参考状态：无线上参考已确认
视觉基线：按新页面概念稿和默认生产基线延展
```

## 追问题库

只选择当前任务真正需要的问题。

### 用户问题

- 这个屏幕要解决哪个具体用户问题？
- 用户来到这里前一刻正在做什么？
- 什么会让用户觉得“这个页面帮我做了决定或采取了行动”？

### 现状替代方案

- 用户今天是怎么替代解决的，哪怕很手工、很混乱？
- 当前替代方案造成了什么成本：时间、金钱、风险、困惑、客服压力、流失？
- 如果用户忽略这个功能，会发生什么？

### 目标与指标

- 这个设计必须提升哪个主行为或主指标？
- 哪个反指标能防止团队“作弊式”优化目标？
- 在提升主指标时，什么不能变差？

### 用户任务

- 用户在这个屏幕上必须完成的最小任务是什么？
- 用户信任下一步动作前，必须先看到什么信息？
- 哪些内容可以放到主动作之后，而不伤害任务完成？

### 证据

- 什么证据说明这是真问题：通话记录、投诉、流失数据、重复客服工单、观察行为？
- 哪句用户原话或哪个用户行为应该影响文案和层级？
- 当前最弱的假设是什么？

### 约束

- 哪些业务、合规、数据、运营或技术约束不能改变？
- 哪些现有组件、设计系统或生产模式必须复用？
- 哪些功能因为无法交付，不能出现在原型里？

### 数据

- 哪些数据可以立即展示？
- 哪些数据需要个性化、新鲜度、库存、资格判断或人工确认？
- 哪些数据是估算，应该如何标注不确定性？

### 方案方向

- 原型应该由哪种产品策略主导：降低摩擦、增强信任、强化对比、明确状态、丰富报告、加快任务完成，还是制造更强惊喜？
- 哪个方向应主动避免，因为它不符合品牌、不可行，或优化了错误指标？
- 多方案任务里，哪 2-4 个方向有足够本质差异，值得比较？

## 对齐状态

继续前使用以下状态之一：

- `需要补充`：一个或多个诊断问题还会实质改变原型；继续问一个聚焦的 `Q`。
- `待确认`：已有足够上下文；输出前提确认、当前待拍板 `D` 或短产品简报，请用户确认、修改或批准假设。
- `已对齐`：用户在对话里确认计划、编辑/批准了 Zoon 产品简报，或明确说使用列出的假设。

只有 `已对齐` 可以进入设计系统检查、对抗审查、图片提示词或图片生成。

## 前提确认

创建产品简报前，先把最关键的产品判断压缩成 2-4 条前提，让用户同意、不同意或修改。前提必须能改变后续原型，而不是复述事实。

```text
前提确认：
1. <关于用户问题或真实损失的判断>。同意 / 不同意 / 修改？
2. <关于目标、反指标或承诺边界的判断>。同意 / 不同意 / 修改？
3. <关于最小有价值版本或方案方向的判断>。同意 / 不同意 / 修改？
```

如果用户不同意任一前提，先修正理解并回到相关 `Q` 或 `D`。未完成前提确认时，产品简报不能标记为 `已对齐`。

## 简短输出

创建产品简报前，先这样汇总：

```text
对齐状态：
产品意图：
- 工作目标模式：
- 变化类型：<新功能 / 现有功能迭代 / 不明确>
- 现状基线：<已提供截图 / 缺失 / 不适用>
- 线上参考需求：<需要 / 不需要 / 待判断>
- 线上参考状态：<已提供线上参考 / 无线上参考已确认 / 缺失待补充 / 不适用>
- 场景路由：
- 用户问题：
- 用户任务：
- 主目标：
- 反指标：
- 当前阻力：
- 硬约束：
- 可用数据：
- 方案方向：
- 已确认前提：
- 当前 Q / 当前 D / 后续 D 队列：
- 设计影响：
```

把这段摘要写入产品简报。产品简报已对齐后，把它用于图片提示词里的产品意图部分。

## 产品简报交接

完成产品追问对齐后，创建或更新可编辑产品简报：

- **快速版产品简报：** 小范围截图迭代、窄页面改动或单个决策。
- **标准版产品简报：** 大多数需要沉淀产品意图和约束的原型请求。
- **深度版产品简报：** 新功能、高风险流程、跨团队协作、证据不清或涉及敏感数据/运营。

不要把产品简报当成固定 PRD 模板。它是协作资产，用来记录当前理解、假设和 PM 决策点，也是下一步原型的产品契约。

清楚标记不确定区域：

- `当前假设：` 助手推断出来的内容。
- `请补充：` 缺失信息。
- `请拍板：` 需要产品取舍。
- `不可虚构：` 无法支持的能力或数据。

自适应产品简报结构和 Zoon 交接规则见 `product-plan-handoff.md`。
