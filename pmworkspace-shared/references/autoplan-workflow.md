# 自动产品评审流水线

`$pm-autoplan` 使用本文件。目标是把 PMWorkspace 从“用户手动选择下一个 skill”升级为“自动识别当前最早缺口，并只在关键产品取舍处停下”。它支持两个入口：快速成型和深度交付。

## 模式选择

- **快速成型：** 用户有一句 idea、拍脑袋方案、想先看几个方案、想要 10 分钟轻量包，或输出目标是“产品简报 + 方案方向 + 原型图”。目标是快速产出可讨论资产。
- **深度交付：** 用户要 PRD、设计评审、研发交付、Zoon 协作、生产截图迭代、线上流程或高风险业务。目标是沉淀可交付事实来源。

多个信号并存时，优先识别用户当前要解决的最近任务：如果是“先拿出去讨论”，选快速成型；如果是“要交付给下一团队”，选深度交付。

`$pm-autoplan` 不重复维护 D0 规则。入口来自 `$pm-workspace` 时，复用当前 run 和主入口已经判定的模式；用户直接调用 `$pm-autoplan` 时，读取 `routing.md` 的 D0 工作方式判定，并在没有当前 run 时创建 run。

## 靠谱产品负责人定义

`$pm-autoplan` 的默认姿态是 `平衡总控`。它像一个靠谱产品负责人：能自动推进低风险事项，但不越过事实、承诺、风险和交付门槛。

靠谱产品负责人必须满足：

- **事实优先**：已对齐产品简报 / 最新 Zoon / 用户本轮明确输入优先于历史偏好；历史偏好只能影响推荐方式，不能覆盖当前事实。
- **结论明确**：用户可见输出先给 `自动评审结论`，说明 `我建议` 和 `理由`，不能只输出字段表或维护日志。
- **自动但不越权**：低风险、可逆、不改变方向的默认项可以自动采用；用户承诺、数据真实性、范围、实验口径、线索 / 交易 / 隐私 / 合规必须进入一个当前 `D`。
- **最早门槛优先**：每轮只处理一个最早阻塞门槛，不假装完整链路都已完成。
- **交接负责**：交给下一技能时，必须带上 `来源门槛`、`已确认事实`、`未决 Q/D`、`证据状态` 和 `交给它的原因`。

结论先行不是省略审计字段；它是先让用户看懂判断，再给出评审控制面板。

## 自动评审控制器

自动产品评审每轮先产出一个内部控制面板，再决定是自动推进还是停下：

```text
模式来源
-> 事实来源优先级
-> 当前阶段
-> 最早阻塞门槛
-> 门槛等级
-> 门槛来源
-> 可自动采用项
-> 必须 PM 拍板项
-> 下一技能
-> 交接上下文
```

控制器规则：

- 只推进已经由产品简报、最新 Zoon、用户本轮输入、已确认 Q/D 或当前 run 证据支持的事项。
- 每轮只处理一个最早阻塞门槛；不要为了显得完整而同时展开多个 `Q` 或多个 `D`。
- 如果当前请求暴露生产流程、高风险承诺、真实数据、线索/交易/隐私或研发交付信号，即使用户说“快速”，也升级到深度交付门槛。
- 如果信息足以低风险推进，就自动采用默认项并记录；如果会改变产品方向、承诺、实验口径、范围或交付责任，就停在一个 `D`。
- 如果缺少事实导致无法形成有意义选项，先问一个 `Q`，不要用 `D` 假装可以拍板。

## 门槛等级

每个最早门槛都必须标注等级和来源：

- `阻断`：不处理就不能继续，例如产品简报未 `已对齐`、线上参考缺失、Zoon 实质漂移、image-2 前门槛未过。
- `高风险`：可能影响用户承诺、数据真实性、隐私、交易、线索、合规、实验口径或交付验收，需要一个当前 `D`。
- `可自动采用`：低风险、可逆、不改变产品方向、用户承诺或数据边界，可以记录后继续推进。
- `可延后`：不影响当前下一步，可交给后续技能处理，但必须写入交接上下文。

门槛来源只能来自：用户本轮输入、已对齐产品简报、最新 Zoon、当前 run 证据、线上参考、原型复审、PMWorkspace 默认规则或历史偏好。历史偏好不能作为阻断门槛的唯一来源。

## 自动采用质量

每个自动采用项都必须说明来源和不需要 PM 拍板的理由：

```text
默认移动端优先。来源：PMWorkspace 默认规则。原因：不改变产品方向或用户承诺。
```

如果某个自动采用项无法说明来源或原因，就不能自动采用；把它降级为 `需要补充` 或当前 `D`。

## 下一技能交接

`下一技能` 不能只写 skill id。交接摘要必须包含：

- `来源门槛`：触发交接的最早门槛。
- `已确认事实`：可以被下游直接复用的事实。
- `未决 Q/D`：当前问题、当前选择题或后续 D 队列。
- `证据状态`：产品简报、Zoon、线上参考、原型清单、待决策项。
- `交给它的原因`：为什么这个门槛应该由该技能处理。

## 快速成型流水线

```text
输入识别
-> 2-3 个关键 Q
-> 假设确认
-> 轻量产品简报
-> 2-3 个方案方向
-> image-2 原型图计划
-> 下一步升级建议
```

快速成型的轻量包必须包含：

- 产品简报：标注 `基于假设，可讨论`，列出当前假设、主目标、反指标和不可虚构项。
- 方案方向：2-3 个方向，差异必须来自页面结构、信息架构、交互路径、信任表达或关键任务。
- 原型图计划：每个方案默认 1 张移动端图；每张图绑定方案名、屏幕任务、主目标、反指标、不可虚构项和简报版本。
- 升级建议：继续补齐 PRD、进入原型复审，或整理成设计/研发交付稿。

快速成型出图前必须让用户确认：`按这些假设继续`。确认前只能输出轻量包计划，不能生成图片。

快速成型最早门槛顺序：

1. 生产/高风险升级检查。
2. 核心用户或场景。
3. 核心问题和当前损失。
4. 主目标、反指标和不可虚构项。
5. 原型屏幕范围。
6. 方案差异是否来自页面结构、信息架构、交互路径、信任表达或关键任务。
7. 假设确认：用户明确同意“按这些假设继续”。

快速成型只问最影响轻量包结构的 2-3 个 `Q`。如果 3 个 `Q` 后仍缺少反指标、不可虚构项或屏幕范围，输出 `需要补充`，不要硬凑轻量包。

## 深度交付流水线

```text
输入识别
-> 工作目标模式
-> 场景路由
-> Q 诊断缺口
-> 前提确认
-> D 拍板
-> 策略审查
-> 产品简报
-> Zoon 同步
-> Zoon 漂移检查
-> Product Readiness Dashboard
-> 原型准备度 / 交付准备度
```

深度交付最早门槛顺序：

1. 工作目标模式。
2. 场景路由。
3. Q 诊断缺口。
4. 前提确认。
5. 必要 D 拍板。
6. 策略审查：只有范围、价值交换、风险或定位会 materially 改变方向时才进入。
7. 产品简报：必须达到 `已对齐` 才能进入图片提示词。
8. Zoon 同步和漂移检查。
9. 线上参考和设计系统基线。
10. 运行 Product Readiness Dashboard，统一展示 brief、Zoon、线上参考、方案差异、不可虚构项和复审状态。
11. 原型准备度或交付准备度。

深度交付不是每轮都把所有子流程跑完。每轮只推进到“最早仍不可靠的门槛”，并把下一步映射到一个技能：

| 最早门槛 | 下一技能 |
|---|---|
| 工作目标、场景、Q 诊断、前提确认 | `$pm-jobs` |
| 范围、价值交换、信任、反指标、可行性风险 | `$pm-strategy-review` |
| 产品简报缺失、未确认或 Zoon 需要同步 | `$pm-brief` |
| 已对齐且需要原型方案 | `$pm-prototype-shotgun` |
| 原型已生成且需要验收 | `$pm-prototype-review` |
| 方向已选定且要交给下一团队 | `$pm-handoff` |

进入 `$pm-prototype-shotgun` 前，`pmw-dashboard readiness --target prototype` 的 verdict 必须是 `可出图`；进入 `$pm-handoff` 前，`pmw-dashboard readiness --target handoff` 的 verdict 必须是 `可交付`。若不是，下一技能指向仪表盘第一条阻断门槛对应的技能。

## 自动推进边界

可以自动推进：

- 用户材料已经明确回答的问题。
- 不改变产品方向的默认格式、画布和字段。
- 产品简报发布时优先推送 Zoon；已有 Zoon URL 时优先追加，不创建新文档。
- 已有产品简报且用户要求继续时，先做漂移检查。
- 快速成型模式中的轻量包默认结构和默认移动端画布。

必须停止：

- 缺少会改变产品结构的事实。
- 缺少会改变范围、承诺、实验口径或数据边界的决策。
- 线上参考需要但缺失。
- Zoon 最新内容与本地 brief 不一致。
- 深度交付模式中，产品简报不是 `已对齐`，但用户要求出图或交付。
- 快速成型模式尚未获得用户确认“按这些假设继续”，但即将生成图片。
- 快速成型输入出现生产流程、高风险承诺、真实数据、线索/交易/隐私或研发交付信号，需要升级到深度交付门槛。
- 深度交付的最早门槛尚未通过，但用户要求跳到原型、HTML、交付稿或完整 PRD。

## 完成态

- `需要补充`：必须先拿输入或参考。
- `待确认`：已有推荐和假设，等待用户确认。
- `基于假设，可讨论`：快速成型轻量包已经确认，可用于讨论，但不是最终 PRD 或已验证事实。
- `已对齐`：产品简报可以作为事实来源。
- `可进入原型复审`：已生成图片，下一步应走 `$pm-prototype-review`。

## 输出原则

- 默认采用 `结论先行 + 评审控制面板`，先讲建议和理由，再给字段。
- 不批量展开多个 `D`。
- 不用长开放问题清单替代下一步。
- 不把自动判断包装成用户已确认的事实。
- 如果自动创建或追加 Zoon 失败，保留本地 brief 审计副本，并把脱敏失败原因写进状态。
- 每次输出必须包含 `自动评审结论`、`我建议`、`理由`、`推进阶段`、`模式来源`、`最早门槛`、`门槛等级`、`门槛来源`、`自动采用项`、`停止原因`、`下一技能`、`交接上下文` 和 `证据状态`。
- 如果继续用当前 run，输出当前 `run_id`；如果脚本不可用，写 `运行审计：未启用`。
