# 产品交付控制器

`$pm-handoff` 使用本文件把已对齐产品简述 / 产品简报、已选原型方向、三条产品路径原型图和复审结论整理成产品设计文档、PRD、设计交付、实验验证或研发交付稿。交付稿是下一团队的执行契约，不是讨论稿，也不是把未解决问题包装成验收标准。

`$pm-handoff` 默认是 **精简 PRD 交付官**；当上游已经完成 image-2 原型图和复审，或用户要求“产品设计文档 / 设计方案文档 / 原型方案说明”时，它切换为 **产品设计文档交付官**，把产品判断、三条产品路径、原型图、设计完整度、设计思考和产品判断演进整理成最终产品设计文档。

默认 PRD 的目标是少而准：只写会影响执行的核心信息，缺口清楚留空，风险门槛不虚构。

## 交付控制器

生成交付稿前，先建立交付控制器。控制器至少记录：

- `交付目标`：产品设计文档、PRD、设计交付、实验验证、研发交付，或它们的组合。
- `事实来源`：已对齐产品简报版本、最新 Zoon 快照、策略决策、产品判断对抗校验结论、prototype-board 选定方向、原型设计完整度、原型可信度对抗复审结论和原型复审结论。
- `Product Readiness Dashboard`：用 `pmw-dashboard readiness --target handoff` 在交付前统一检查产品简报、Zoon、线上参考、方案差异、不可虚构项和复审状态；verdict 不是 `可交付` 时不能继续写 PRD 或验收。默认只展示短 verdict 和第一阻断原因，完整表格只在审计 / 调试时展开。
- `交付前门槛`：产品简报已对齐、Zoon 无实质漂移、线上参考门槛通过、原型复审通过、关键 D 已拍板、不可虚构项完整。
- `原型复审状态`：可通过、需要重出、需要 PM 拍板、需要补充参考，或不适用（无原型交付）。
- `未决拍板`：仍会改变范围、用户承诺、实验口径、数据真实性、线索/交易/隐私/合规边界或验收标准的 D。
- `交付类型`：选择 PRD、设计、实验或研发模板；只输出当前需要的深度，不把所有模板硬塞进一份文档。
- `现成文档参考`：用户是否提供 PRD、接口文档、埋点方案、实验方案、Zoon、截图或等价资料；未提供时不阻断精简 PRD，但要标明按当前 brief 生成。
- `研发可行性反问`：交付前模拟研发会向产品追问的能力依赖，覆盖数据来源、接口能力、算法 / 推荐能力、规则口径、权限、后台配置、运营支持、埋点日志、异常 / 空态和合规边界。
- `功能能力与研发依赖`：把每个功能承诺拆成所需能力、当前状态、事实来源、责任归属、是否阻断和处理动作；不能把未知或未具备能力写成已支持。
- `PRD 缺口处理`：缺接口、数据字段、埋点属性或实验细节但不改变承诺时，保留空值并列入 `待补充项`；会改变承诺或验收的缺口必须进入当前 `D`。
- `验收写入边界`：只把已确认范围、已支持能力、已拍板承诺和已通过复审的屏幕写入验收标准。
- `范围外`：明确不做什么、未来再做什么、不能虚构什么。
- `交付资产沉淀`：从用户输入和交付稿中提取接口、数据来源、指标口径、埋点事件、实验标准和数据可用性判断，写入本地脱敏资产。
- `交付后协作选择`：交付稿保存后推荐 Zoon 在线协作，但不自动同步、不阻断本地 Markdown；每次让用户选择暂不需要、同步到已有 Zoon 文档或新建 Zoon 交付文档。
- `下一技能`：门槛未过时退回 `$pm-brief`、`$pm-prototype-review` 或 `$pm-strategy-review`；门槛通过时生成交付稿。
- `证据状态`：产品简报、Zoon、线上参考、原型清单、复审结论、D 决策、不可虚构项和保存状态。

交付控制器只写入内部审计、本地状态或调试输出，不进入 PRD 正文。用户可见 PRD 顶部只保留轻量 `交付结论`，不要输出 `PRD 生成判断`、run_id、完整准备度表、产物流动或本地资产路径。`Zoon 协作建议` 和 `在线协作选择` 是交付完成后的下一步提示，不写进 PRD 正文。

## 现成文档入口

当用户要 PRD、研发交付、实验标准、埋点或接口梳理时，先给一个轻量入口提示：

```text
如果你有现成 PRD、接口文档、埋点方案、实验方案、Zoon 或截图，可以上传给我参考；没有的话，我会基于当前已对齐 brief 生成精简 PRD，并把缺失项留空待补充。
```

这不是新增硬门槛。用户没有文档时，可以继续基于已对齐 brief 生成精简 PRD；只有缺口会改变范围、用户承诺、数据真实性、实验口径、线索/交易/隐私/合规边界或验收标准时，才必须停止在 `需要 PM 拍板`。

## 研发可行性反问内核

研发可行性反问不是替研发做架构设计，而是在 `$pm-handoff` 写 PRD / 研发交付稿前，提前模拟研发会向产品追问的业务事实和能力前提。它只在交付前触发，不前置到产品方向审查或原型探索。

每个功能承诺都要检查背后的真实依赖：

- `数据来源`：来自实时接口、离线表、人工录入、第三方、用户输入、估算还是暂无数据。
- `接口能力`：已有接口、需配置、需改造、需新建，或接口归属未知。
- `算法 / 推荐能力`：当前是否已有推荐、排序、预测、匹配或评分能力；没有时不能画成已支持。
- `规则口径`：规则、阈值、适用范围、优先级和冲突处理是否已定义。
- `权限与后台`：是否需要用户授权、员工权限、后台配置、审核流或管理端能力。
- `运营支持`：人工确认、客服处理、商家协作、库存维护、内容配置或风控审核是否需要运营承接。
- `埋点与日志`：关键行为、异常状态、失败原因和反指标是否能记录。
- `异常 / 空态`：缺数据、过期、冲突、不符合资格、接口失败、人工未处理时如何展示。
- `合规边界`：隐私、资质、价格、金融、医疗、版权、平台政策或对外承诺是否有限制。

反问结果只能落入四类：

- `产品需补齐`：需要产品补规则、口径、数据来源、运营流程、合规边界或验收写法。
- `研发需评估`：需要研发评估接口、算法、后台、性能、权限或日志实现方案；产品不能代写技术结论。
- `可留待补充`：缺口不改变用户承诺、数据真实性、算法能力、合规边界或验收标准，可在 PRD 中留空为 `待补充`。
- `不可写入验收`：能力未知、未具备或未拍板，且会影响承诺 / 验收；必须进入当前 `D`、降级方案或退回 `$pm-strategy-review`。

能力依赖表中的 `当前状态` 只允许使用：已具备、需配置、需改造、需新建、未知、不可承诺。`处理动作` 只允许使用：写入验收、保留待补充、降级方案、当前 D、退回策略审查。

如果研发可行性反问发现选中路径的成本、能力或数据前提不成立，不能静默改方案。应退回 `$pm-strategy-review`，用收缩、转向或选择性扩大重新拍板。

平台脚本可用时，完成反问后用现有 run 事件登记，不新增 artifact 类型：

```bash
pmw-run event --type gate --status "已完成" --title "研发可行性反问" --summary "功能能力与研发依赖已审查；普通缺口进入待补充，影响承诺或验收的缺口已转 D / 降级 / 退回策略审查"
```

## 待补充项交互

普通交付缺口不阻断精简 PRD。PRD 正文保留待补充项列表，并在 `下一步：待补充决策清单` 中引导用户继续补充：

- 每项状态只能是 `待补充`、`已跳过` 或 `已补充`。
- 用户可以回复 `跳过某项` 或 `全部先跳过`；被跳过的普通缺口保持在 PRD 待补充项中，不阻断交付。
- 用户补充某项后，更新对应状态为 `已补充`，并把接口、数据、埋点、实验等信息按脱敏规则沉淀为交付资产。
- 如果某项缺口会改变范围、用户承诺、实验口径、数据真实性、线索 / 交易 / 隐私 / 合规边界或验收标准，不能标记为 `已跳过`，必须升级为一个当前 `D`。

## 交付后协作选择

PRD / 产品设计文档生成并用 `pmw-log handoff` 保存后，默认强推荐 Zoon，但不自动同步、不作为交付阻断。本地 Markdown 已经是可用交付稿；Zoon 是团队继续修改、评审、研发对齐和让 PMWorkspace agent 一起改文档的协作层。

用户可见输出必须包含：

```text
Zoon 协作建议：PRD / 产品设计文档已经保存为本地 Markdown。建议同步到 Zoon，让团队在线修改，并让 PMWorkspace agent 加入文档继续协助完善接口、埋点、实验标准和待补充项。不同步也不影响继续使用本地 Markdown。

在线协作选择：
A. 暂不需要，继续使用本地 Markdown。
B. 同步到已有 Zoon 文档（提供 URL 或使用项目已记录 URL）。
C. 新建一个 Zoon 交付文档。
```

用户选择 B/C 后再执行 Zoon 写入：

- B：优先追加到用户提供的 Zoon URL；如果未提供但项目已记录 `zoon_url`，询问用户确认后使用该 URL；已有本地交付稿路径时可用 `pmw-zoon sync --title "PRD：<需求名>" --url "<Zoon URL>" --document "<PRD.md>"`。
- C：用 `pmw-zoon create --title "PRD：<需求名>"` 或 `pmw-zoon create --title "产品设计文档：<功能名>"` 新建交付文档。
- 创建或追加成功后，`pmw-zoon` 必须自动执行 `join` / presence，让 `pmworkspace` agent 加入协作态，并优先打开 Codex 内置浏览器。
- 如果自动加入失败或服务不支持，输出：`已创建/已同步，但 agent 自动加入失败/不支持，请在文档编辑页手动邀请或继续用本地 Markdown`。手动邀请只是兜底，不是默认流程。
- Zoon 同步失败时，保留本地 Markdown 和 artifact-flow 登记，简短说明失败原因，不打印 token、ownerSecret 或 API 原始响应。

## 硬门槛

- 产品简报不是 `已对齐` 时，不输出 PRD、设计交付、实验方案或研发验收；退回 `$pm-brief`。
- Zoon 漂移改变目标、反指标、不可虚构项、范围、用户承诺或方案方向时，不能沿用旧交付稿；退回 `$pm-brief` 或 `$pm-strategy-review`。
- 交付依赖原型图时，原型复审必须是 `可通过`；如果是 `需要重出`，退回 `$pm-prototype-shotgun`；如果是 `需要 PM 拍板`，先问一个当前 `D`；如果是 `需要补充参考`，先补参考。
- Product Readiness Dashboard 的任一 required 行未通过时，按第一条阻断行退回最早技能，不输出交付稿、实验口径或研发验收标准。
- 关键 D 未拍板时，不能写研发验收标准、实验口径或对外承诺；只输出待决策和一个当前 `D`。
- 研发可行性反问未完成时，不输出研发验收标准；先补 `功能能力与研发依赖`。如果某个能力缺口会改变用户承诺、数据真实性、算法能力、合规边界或验收标准，不能标记为普通待补充，必须进入当前 `D`、降级方案或退回 `$pm-strategy-review`。
- 不可虚构项、数据真实性和合规边界不能用“后续确认”糊进验收标准；它们必须作为范围外、风险或待决策。

## 交付类型模板

### 产品设计文档

在原型图和复审后生成，作为最终交付物。它必须读取 `product_brief`、产品评估中的对抗校验结论、`prototype_manifest`、prototype-board、`prototype_review`、原型可信度对抗复审结论、线上参考、视觉基线和数据 / 访谈 / 截图 / 竞品启发；同时沉淀每个方案的设计完整度评分、10/10 原型标准、prompt 修正方向、状态覆盖、信息层级和反 AI 模板味约束。不能在产品简述未确认、原型设计完整度缺失或原型复审未通过时生成最终版。


### PRD 交付

默认输出精简 PRD。核心只保留本周期承诺。单功能默认使用 `1-2 周` 验证 / 交付口径；只有跨模块、大功能或产品线规划才使用 `1-3 个月`，并且不得把 1-3 个月内容写成本周期验收。

核心只保留：

- 需求背景
- 需求价值
- 需求方案
- 需求功能及描述
- 功能能力与研发依赖
- 接口以及数据来源
- 埋点信息
- 实验标准
- 待补充项
- 不可虚构

默认不写测试计划、开发周期、排期、人力、会议纪要或长篇风险清单；用户明确要求时再追加。

```markdown
- 准备度：
```

### 缺口处理

- 缺接口名、字段、埋点属性、实验周期或数据新鲜度，但不改变产品承诺时，保留空值，写 `待补充`。
- 用户输入中没有接口、数据、埋点或实验信息时，不要虚构；在对应表格留下空行或 `待补充`，并在 PRD 后用待补充决策清单提醒用户可补充、跳过某项或全部先跳过。
- 如果缺口会改变范围、用户承诺、实验口径、数据真实性、线索/交易/隐私/合规边界或验收标准，不能留空绕过，必须问一个当前 `D`。
- 用户上传的现成文档只作为事实来源或口径参考；不要把完整私密 PRD、内部 URL、token、客户信息或截图内容写入公开仓库。

### 设计交付

必须包含：

- 选定方案方向
- 已通过复审的原型清单
- 每屏任务、主目标、反指标和不可虚构项
- 设计系统 / 线上参考状态
- 需要重出或待拍板的屏幕（如果有，不能进入最终交付）
- 设计后续需要保留、弱化或补充的内容

### 实验验证

必须包含：

- 实验假设
- 目标人群与入口
- 主指标、反指标和护栏指标
- 样本、周期或判断口径
- 风险和停止条件
- 不可虚构项和数据真实性说明

### 研发交付

必须包含：

- 实现范围
- 状态、异常和空态
- 功能能力与研发依赖
- 数据字段、来源和新鲜度
- 依赖、权限、埋点和日志
- 验收标准
- 不做项和风险

## 验收标准规则

验收标准只写可以执行和验证的内容：

- 使用“当 / 如果 / 则”结构描述行为、状态和边界。
- 每条验收都能追溯到已对齐产品简报、已拍板 D、已通过复审的原型或明确的线上参考。
- 每条验收必须能对应 `功能能力与研发依赖` 中状态为 `已具备`、`需配置` 或已拍板的能力；`未知`、`需新建` 且未评估、`不可承诺` 的能力不能写入验收。
- 不把未支持能力、未拍板承诺、未验证数据、待定实验口径或未来方案写成验收。
- 如果发现会改变验收的未决问题，停止在 `需要 PM 拍板`，只展开一个当前 `D`。

## 保存与审计

平台脚本可用时：

```bash
pmw-log handoff "<功能名>"
pmw-memory add-delivery-fact --fact-type tracking --note "<脱敏埋点事件或指标口径>" --scenario "<场景>" --target "<对象>" --scope "本项目" --source "产品交付" --confidence 0.5
pmw-memory add-delivery-fact --fact-type experiment --note "<脱敏实验标准>" --scenario "<场景>" --target "<实验对象>" --scope "同类场景可复用" --source "产品交付" --confidence 0.5
pmw-run event --type gate --status "已完成" --title "研发可行性反问" --summary "<功能能力与研发依赖审查结果>"
pmw-log handoff "<产品设计文档标题>" --artifact-kind product_design_doc
pmw-run event --type artifact --status "可交付" --title "产品交付稿" --summary "<交付类型与版本>"
pmw-run finish --status "可交付" --next "<下一步>"
```

`pmw-log handoff` 只保存本地交付稿并登记 artifact，不自动创建或更新 Zoon。只有用户在交付后协作选择中选择 B/C，才调用 `pmw-zoon append|create|sync`。

如果脚本不可用，在输出里标记 `已保存资产：未保存（脚本不可用）`。

## 交付资产沉淀

用户输入的信息要尽量保留成可复用资产，尤其是埋点、实验、接口和数据情况。第一版保存脱敏摘要，不保存原始文档：

- `interface`：接口名、能力边界、调用来源、依赖状态。
- `data-source`：数据来源、字段口径、新鲜度、可用性判断。
- `capability-dependency`：功能承诺、所需能力、当前状态、责任归属、阻断状态和处理动作。
- `tracking`：埋点事件、触发时机、属性、指标用途。
- `experiment`：实验假设、人群、主指标、反指标、判断标准、停止条件。
- `metric-definition`：指标定义、分子分母、过滤条件、统计窗口。

每条交付资产必须包含 `fact-type`、`scenario`、`target`、`scope`、`source` 和 `confidence`。本项目事实写入项目目录；同类场景可复用的脱敏口径可以写入用户全局目录。交付资产是参考和推荐来源，不是事实来源；当前已对齐 brief、最新 Zoon、本轮输入、反指标和不可虚构项永远优先。
