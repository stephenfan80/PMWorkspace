# PM Review Army / Product Review Squad

PM Review Army 是结构化多视角复审协议。它的产品形态是 **可插拔复审专家 + Product Review Squad**：不要求真实多 agent 并行，但必须让不同专家和职能角色独立暴露盲区，再由 `$pm-prototype-review` 合并成行动建议。

目标不是让一个强 PM 替所有人做判断，而是在出图、复审和交付前模拟一支跨职能产品小队：CEO、工程、设计、DX、安全、QA、发布工程师各司其职。

## 可插拔专家协议

四个产品原型底盘视角必须像 gstack specialist 一样各自产出短结论，不能折叠成一段 PM 总评。默认专家是：

| expert id | 中文名 | 关注点 | 默认适用 |
|---|---|---|---|
| `strategy` | 策略专家 | 目标用户、核心问题、价值交换、范围取舍、方案是否仍解决真实问题 | 所有原型复审 |
| `trust-risk` | 信任 / 风险专家 | 反指标、不可虚构项、数据承诺、隐私、用户预期和信任损耗 | 所有原型复审 |
| `design-system` | 设计系统专家 | 生产样式、信息层级、组件合理性、可读性、移动端可用性 | 所有原型复审 |
| `data-feasibility` | 数据可行性专家 | 页面数据、自动化能力、资格判断、计算口径和接口可兑现性 | 所有原型复审 |

专家短结论使用统一结构：

```text
- <专家>：结论=<可通过 / 需要重出 / 需要 PM 拍板 / 需要补充参考>；最高严重度=<P0/P1/P2/P3>；证据=<brief / Zoon / 截图 / 原型图 / prototype-board / 缺失>；一句话判断=<...>；行动=<删除 / 前置 / 后置 / 标注 / 补证据 / 拍板 / 重出 / 可交付>
```

平台脚本可用时，每个专家短结论写入本地项目资产：

```bash
pmw-review-specialist add \
  --expert strategy \
  --status "需要重出" \
  --severity P1 \
  --evidence "brief + 原型图" \
  --judgment "<一句话判断>" \
  --action "重出" \
  --scheme "<方案名>" \
  --screen "<屏幕任务>"

pmw-review-specialist summary
```

允许后续新增专家，但新增专家不能替代四个默认专家。可插拔专家只登记元数据、短结论和证据来源，不写入私密 brief 正文、Zoon 正文、token、ownerSecret、内部 URL 或未脱敏截图内容。

## 角色分层

PMWorkspace 使用两层 reviewer：

1. **可插拔产品原型专家**：策略、信任 / 风险、设计系统、数据可行性。适用于所有原型复审。
2. **跨职能 Product Review Squad**：CEO、Eng、Design、DX、安全、QA、发布工程师。适用于高风险、批量交付、研发交付、生产流程、真实数据、线索 / 交易 / 隐私 / 合规、上线发布或用户要求“多角色 review”的任务。

轻量低风险讨论可以只跑四个可插拔产品原型专家，但如果进入深度交付、原型验收或 PRD / 研发交付，必须追加 Product Review Squad。

## 默认产品原型专家

- **策略专家**：检查目标用户、核心问题、价值交换、范围取舍是否成立。
- **信任 / 风险专家**：检查反指标、不可虚构项、数据承诺、隐私和用户预期。
- **设计系统专家**：检查生产样式、信息层级、组件合理性、可读性和移动端可用性。
- **数据可行性专家**：检查页面展示的数据、自动化能力、资格判断和计算口径是否可兑现。

## Product Review Squad 角色

每个角色必须输出短结论，而不是长篇报告。短结论使用同一结构：

```text
- <角色>：结论=<通过 / 需要重出 / 需要 PM 拍板 / 需要补充参考>；最高严重度=<P0/P1/P2/P3>；证据=<brief / Zoon / 截图 / 原型图 / 缺失>；一句话判断=<...>；行动=<删除 / 前置 / 后置 / 标注 / 补证据 / 拍板 / 重出 / 可交付>
```

角色职责：

- **CEO reviewer**：判断战略价值、目标用户、价值交换、商业优先级和是否值得占用团队资源。发现“不是当前最该做的问题”时，结论至少是 `需要 PM 拍板`。
- **Eng reviewer**：判断技术可行性、系统依赖、接口 / 数据来源、边界状态、降级方案和研发复杂度。发现无法兑现的自动化、计算、推荐或状态承诺时，结论至少是 `需要重出` 或 `需要 PM 拍板`。
- **Design reviewer**：判断信息架构、交互路径、视觉层级、设计系统一致性、可读性、可访问性和移动端可用性。发现设计系统实质偏离或任务路径不可用时，结论至少是 `需要重出`。
- **DX reviewer**：判断协作和开发体验，包括 PRD 可读性、交接摩擦、接口命名、埋点可调试性、错误定位、运营 / 研发 / 设计继续工作的上下文是否足够。发现下游无法接手或验收口径不可追踪时，结论至少是 `需要补充参考` 或 `需要 PM 拍板`。
- **安全 reviewer**：判断隐私、权限、数据最小化、滥用、合规、敏感信息、用户承诺和安全边界。发现隐私、合规、交易、线索或敏感数据边界未决时，结论至少是 `需要 PM 拍板`。
- **QA reviewer**：判断验收标准、空 / 错 / 加载 / 超时状态、异常路径、回归风险、跨端适配和可测试性。发现关键状态缺失会误导验收时，结论至少是 `需要重出` 或 `需要补充参考`。
- **发布工程师 reviewer**：判断发布准备度、灰度、开关、回滚、监控、迁移、依赖和上线顺序。发现无法安全上线或回滚边界不清时，结论至少是 `需要 PM 拍板`。

## 合并结论

每个 reviewer 的问题最终必须合并成三类：

- `可通过`：问题不影响产品判断或交付使用。
- `需要重出`：图片或方案违反简报、反指标、不可虚构项、线上参考或设计系统。
- `需要 PM 拍板`：问题来自产品取舍未决，不应靠改图解决。

合并时使用最高严重度，而不是平均分：任一可插拔专家或 Product Review Squad reviewer 发现不可虚构违规、反指标风险、线上参考偏离或设计系统实质偏离，结论至少是 `需要重出`；任一专家发现用户承诺、数据真实性、范围、实验口径、线索/交易/隐私/合规边界未决，结论至少是 `需要 PM 拍板`。

Product Review Squad 的合并优先级：

1. `需要 PM 拍板` 优先于重出：如果问题来自未决产品承诺、范围、实验口径、安全 / 合规 / 发布责任，先问一个当前 `D`，不要写修复提示词。
2. `需要重出` 优先于可通过：如果问题来自已确认事实被图片表达错、违反不可虚构项、设计系统实质偏离或关键状态缺失，只重出受影响屏幕。
3. `需要补充参考` 用于证据缺失：如果角色无法判断是因为缺线上截图、接口文档、埋点方案、发布约束或真实数据边界，先补参考。
4. `可通过` 只能在所有角色都没有 P0/P1 阻断时使用。

只有所有 reviewer 的问题都只是轻微文案、局部密度、对齐或审美偏好时，才允许 `可通过` 并把偏好写入 taste。

## 输出格式

```text
PM Review Army：
- 可插拔专家：
  - 策略专家：
  - 信任 / 风险专家：
  - 设计系统专家：
  - 数据可行性专家：
- 专家合并结论：
- Product Review Squad：
  - CEO reviewer：
  - Eng reviewer：
  - Design reviewer：
  - DX reviewer：
  - 安全 reviewer：
  - QA reviewer：
  - 发布工程师 reviewer：
- 合并结论：
- 需要重出：
- 需要 PM 拍板：
- 需要补充参考：
```

复审的目标不是证明方案没问题，而是用最低成本暴露“现在交付会误导谁”。
