# 产品发现硬门槛

产品发现不是“一问一选后进入简报”，也不是把用户的功能名改写成方案后直接出图。它是一个产品发现任务流：`任务识别 -> 证据收集 -> 用户需求澄清 -> 数据/现状佐证 -> 方案机会判断 -> 产品简述确认 -> 三种产品假设计划`。

`Q` / `D` 只作为关键卡点的交互方式：缺事实时问 `Q`，方向、范围、承诺或实验口径会改变时问 `D`。Agent 在提问前可以先协助用户完成材料整理、线上截图判断、截图结构拆解、访谈提纲、需求假设表、数据口径梳理、最佳实践检索和方案机会归纳。

## 必须覆盖的 5 个事实维度

深度交付、现有线上功能优化、线索 / 交易 / 价格 / 结果页等高风险场景，必须覆盖以下维度后才能生成或确认产品简报：

- `product_role`：产品定位与链路角色。这个能力在链路中负责决策、解释、信任、转化还是交付。
- `target_trigger`：目标用户与触发场景。谁在什么时刻需要这个能力。
- `current_alternative`：用户现状与当前替代。用户今天如何判断、绕路、咨询、等待、比价或放弃。
- `pain_loss`：真实痛点与当前损失。现状造成困惑、时间成本、金钱风险、信任损耗、转化流失还是客服压力。
- `goal_countermetric`：主目标与反指标。要改善什么，同时不能牺牲什么。

如果任一维度缺失，当前门槛就是 `产品发现深度不足`。下一步应回到对应任务：补证据、整理数据、生成访谈提纲、拆解截图，或在确实需要用户判断时问一个当前最大缺口 `Q`；不能进入产品简述确认、image-2 prompt 或交付。

## 发现维度与决策门槛映射

以下门槛是产品发现的最小判定面，不再维护独立决策门槛文档：

- `产品路径`：先判断全新功能、已有功能迭代，或线上流程承接；已有功能迭代必须有当前线上截图、录屏或等价视觉基线。
- `问题真实性`：说明用户问题、当前替代方案和证据强度；证据不足时标记为假设，不能包装成已验证事实。
- `目标与反指标`：定义主行为 / 主指标，同时定义不能变差的信任、质量、投诉、留存、任务成功率、成本或合规护栏。
- `价值交换`：手机号、注册、付款、授权、预约、安装或长流程设置等高成本动作，必须说明行动前用户先得到什么、行动后什么会变好。
- `数据与可行性`：区分可用、估算、推断、用户提供、人工、合作方和不可用数据；不可交付能力不能出现在原型承诺里。
- `场景策略`：确认主场景路由和原型形态；多方案任务在生成图片前，先确认方案差异来自产品策略、信息架构、交互模型或信任模型。
- `产品简述对齐`：用户确认短版产品简述 / 产品简报、批准假设或更新事实来源前，不能进入 image-2 prompt、出图或交付。
- `线上参考`：线上流程下一步、结果页、状态页、活动承接页或生产样式继承场景，必须有线上截图 / 录屏 / 相似页面，或明确记录“无线上参考已确认”。

## Q 与 D 的分工

- `Q` 补事实：用户是谁、触发时刻、当前替代、真实损失、指标、约束。
- `D` 拍取舍：产品定位 / 范围、价值交换 / 信任承诺、数据承诺 / 转化动作、实验口径。
- `D` 不能替代事实诊断；一个 `Q` 加一个 `D` 不能代表产品发现完成。
- 不得把“只问一个 Q 或一个 D”写成产品发现的完整流程；当前卡点如果是材料整理、证据收集、截图分析、数据梳理或访谈准备，就先完成该任务。
- 最终确认产品简报前，深度交付默认至少需要 2 个方向性 `D`。若只有 1 个 `D`，必须记录 `D 豁免原因`；现有线上功能优化默认不豁免。

## 平台记录

可用时用以下命令记录已确认的产品发现维度：

```bash
pmw-log discovery --dimension product_role --source "用户回答 / 截图 / Zoon / 数据" --summary "<事实摘要>" --confidence confirmed
```

候选产品简报声明 `确认状态：已对齐` 前，必须运行：

```bash
pmw-discovery-gate check --target brief --brief <brief.md>
```

如果返回 `blocked`，只能保存 `待确认` 简报或继续 `$pm-jobs`，不能写 image-2 prompt、不能出图、不能交付。
