# 产品简述 / 产品简报模板

产品简述 / 产品简报是出图前用于对齐“这件事怎么判断、建议怎么做、边界在哪里、还有什么会影响方案”的短版业务简报。它不是会议纪要，不是最终产品设计文档，也不是审计日志。

## 推荐结构

默认给用户看的产品简报必须是决策型短简报，不是字段型长清单。深度交付不等于长正文；深度体现在证据、风险、边界和本地审计完整，而不是把所有判断链塞进对话。

用户可见短版业务简报默认只使用以下 6 段；没有证据的判断写 `未提供 / 待验证 / 基于假设`，不能虚构。

```markdown
# 产品简报：{功能名}
状态：草稿 / 待确认 / 已对齐

## 一句话判断
{这件事到底是不是值得做、主路径是什么、当前判断基于事实还是假设。}

## 推荐方案
1. {最多 3-5 条本轮建议。}

## 为什么这样做
- {只保留关键事实、用户损失、核心取舍。}

## 原型范围
- 本轮做：
- 本轮不做：

## 不能虚构 / 不能承诺
- {价格、权益、服务质量、数据能力、结果承诺等边界。}

## 当前需要确认
1. {待确认项标题}
- 还缺什么：
- 为什么影响判断：
- 不补齐的偏差风险：
- 你现在可以怎么做：

## 下一步
- {待确认时要求用户补齐、拍板或明确确认按假设推进；已对齐后才询问是否同步 Zoon。}
```

### 待确认问题卡

只要简报是 `待确认`，`当前需要确认` 必须逐项展示待确认问题卡，禁止只问“是否认可这版简报，并允许按假设继续”。每一项必须包含：

- `还缺什么`
- `为什么影响判断`
- `不补齐的偏差风险`
- `你现在可以怎么做`

已有功能优化如果缺线上截图、关键节点截图、线上页面 URL、Figma / 设计稿或等价视觉基线，第一条待确认问题必须是 `线上截图 / 视觉基线`。如果用户主动提到其他页面或竞品平台但未提供材料，必须追加 `线上 / 竞品基线` 待确认问题，要求截图、URL 或具体可借鉴点。用户可以上传截图后继续，也可以明确确认 `按当前假设先做可讨论原型`；确认后原型状态仍只能写 `基于假设，可讨论`。竞品参考仅作启发，不能覆盖当前线上事实、brief、反指标或不可虚构项。

## 最佳实践压缩原则

- Productboard 类产品简报强调问题、目标用户、当前状态、成功标准和约束。
- Shopify 类产品简报强调用户痛点、市场 / 竞品、目标受众和 KPI。
- Product discovery / customer discovery 强调先理解用户过去行为、当前替代和真实痛点，再讨论方案。
- 公开最佳实践只能作为 `竞品 / 行业做法` 与 `可借鉴原则`，不能覆盖本轮截图、数据、用户回答、反指标或不可虚构项。

## 用户可见与内部审计

用户可见业务简报必须包含 `一句话判断`、`推荐方案`、`为什么这样做`、`原型范围`、`不能虚构 / 不能承诺`、`当前需要确认` 和 `下一步`。产品简报生成后如果还有待确认信息，必须逐项告诉用户缺什么、为什么影响判断、不补齐可能导致哪些产品方案偏差，并要求用户补齐、拍板或明确确认按假设继续。

内部审计继续保存 run、路径、门槛、事实 / 假设边界、Zoon 状态、Product Readiness Dashboard 和产物流动。默认不把本地路径、run_id、token、ownerSecret、未脱敏截图内容或 Zoon 私密正文写入业务简报。
