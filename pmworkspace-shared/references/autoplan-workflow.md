# 自动产品评审流水线

`$pm-autoplan` 使用本文件。目标是把 PMWorkspace 从“用户手动选择下一个 skill”升级为“自动识别当前最早缺口，并只在关键产品取舍处停下”。它支持两个入口：快速成型和深度交付。

## 模式选择

- **快速成型：** 用户有一句 idea、拍脑袋方案、想先看几个方案、想要 10 分钟轻量包，或输出目标是“产品简报 + 方案方向 + 原型图”。目标是快速产出可讨论资产。
- **深度交付：** 用户要 PRD、设计评审、研发交付、Zoon 协作、生产截图迭代、线上流程或高风险业务。目标是沉淀可交付事实来源。

多个信号并存时，优先识别用户当前要解决的最近任务：如果是“先拿出去讨论”，选快速成型；如果是“要交付给下一团队”，选深度交付。

`$pm-autoplan` 不重复维护 D0 规则。入口来自 `$pm-workspace` 时，复用当前 run 和主入口已经判定的模式；用户直接调用 `$pm-autoplan` 时，读取 `routing.md` 的 D0 工作方式判定，并在没有当前 run 时创建 run。

## 自动评审控制器

自动产品评审每轮先产出一个内部控制面板，再决定是自动推进还是停下：

```text
模式来源
-> 事实来源优先级
-> 当前阶段
-> 最早阻塞门槛
-> 可自动采用项
-> 必须 PM 拍板项
-> 下一技能
```

控制器规则：

- 只推进已经由产品简报、最新 Zoon、用户本轮输入、已确认 Q/D 或当前 run 证据支持的事项。
- 每轮只处理一个最早阻塞门槛；不要为了显得完整而同时展开多个 `Q` 或多个 `D`。
- 如果当前请求暴露生产流程、高风险承诺、真实数据、线索/交易/隐私或研发交付信号，即使用户说“快速”，也升级到深度交付门槛。
- 如果信息足以低风险推进，就自动采用默认项并记录；如果会改变产品方向、承诺、实验口径、范围或交付责任，就停在一个 `D`。
- 如果缺少事实导致无法形成有意义选项，先问一个 `Q`，不要用 `D` 假装可以拍板。

## 快速成型流水线

```text
输入识别
-> 2-3 个关键 Q
-> 假设确认
-> 轻量产品简报
-> 2-3 个方案方向
-> image-2 原型图计划
-> 下一步升级建议
```

快速成型的轻量包必须包含：

- 产品简报：标注 `基于假设，可讨论`，列出当前假设、主目标、反指标和不可虚构项。
- 方案方向：2-3 个方向，差异必须来自产品策略、信息架构、交互模型或信任模型。
- 原型图计划：每个方案默认 1 张移动端图；每张图绑定方案名、屏幕任务、主目标、反指标、不可虚构项和简报版本。
- 升级建议：继续补齐 PRD、进入原型复审，或整理成设计/研发交付稿。

快速成型出图前必须让用户确认：`按这些假设继续`。确认前只能输出轻量包计划，不能生成图片。

快速成型最早门槛顺序：

1. 生产/高风险升级检查。
2. 核心用户或场景。
3. 核心问题和当前损失。
4. 主目标、反指标和不可虚构项。
5. 原型屏幕范围。
6. 方案差异是否来自产品策略、信息架构、交互模型或信任模型。
7. 假设确认：用户明确同意“按这些假设继续”。

快速成型只问最影响轻量包结构的 2-3 个 `Q`。如果 3 个 `Q` 后仍缺少反指标、不可虚构项或屏幕范围，输出 `需要补充`，不要硬凑轻量包。

## 深度交付流水线

```text
输入识别
-> 工作目标模式
-> 场景路由
-> Q 诊断缺口
-> 前提确认
-> D 拍板
-> 策略审查
-> 产品简报
-> Zoon 同步
-> Zoon 漂移检查
-> 原型准备度
```

深度交付最早门槛顺序：

1. 工作目标模式。
2. 场景路由。
3. Q 诊断缺口。
4. 前提确认。
5. 必要 D 拍板。
6. 策略审查：只有范围、价值交换、风险或定位会 materially 改变方向时才进入。
7. 产品简报：必须达到 `已对齐` 才能进入图片提示词。
8. Zoon 同步和漂移检查。
9. 线上参考和设计系统基线。
10. 原型准备度或交付准备度。

深度交付不是每轮都把所有子流程跑完。每轮只推进到“最早仍不可靠的门槛”，并把下一步映射到一个技能：

| 最早门槛 | 下一技能 |
|---|---|
| 工作目标、场景、Q 诊断、前提确认 | `$pm-jobs` |
| 范围、价值交换、信任、反指标、可行性风险 | `$pm-strategy-review` |
| 产品简报缺失、未确认或 Zoon 需要同步 | `$pm-brief` |
| 已对齐且需要原型方案 | `$pm-prototype-shotgun` |
| 原型已生成且需要验收 | `$pm-prototype-review` |
| 方向已选定且要交给下一团队 | `$pm-handoff` |

## 自动推进边界

可以自动推进：

- 用户材料已经明确回答的问题。
- 不改变产品方向的默认格式、画布和字段。
- 已有 Zoon URL 时优先追加，不创建新文档。
- 已有产品简报且用户要求继续时，先做漂移检查。
- 快速成型模式中的轻量包默认结构和默认移动端画布。

必须停止：

- 缺少会改变产品结构的事实。
- 缺少会改变范围、承诺、实验口径或数据边界的决策。
- 线上参考需要但缺失。
- Zoon 最新内容与本地 brief 不一致。
- 深度交付模式中，产品简报不是 `已对齐`，但用户要求出图或交付。
- 快速成型模式尚未获得用户确认“按这些假设继续”，但即将生成图片。
- 快速成型输入出现生产流程、高风险承诺、真实数据、线索/交易/隐私或研发交付信号，需要升级到深度交付门槛。
- 深度交付的最早门槛尚未通过，但用户要求跳到原型、HTML、交付稿或完整 PRD。

## 完成态

- `需要补充`：必须先拿输入或参考。
- `待确认`：已有推荐和假设，等待用户确认。
- `基于假设，可讨论`：快速成型轻量包已经确认，可用于讨论，但不是最终 PRD 或已验证事实。
- `已对齐`：产品简报可以作为事实来源。
- `可进入原型复审`：已生成图片，下一步应走 `$pm-prototype-review`。

## 输出原则

- 不批量展开多个 `D`。
- 不用长开放问题清单替代下一步。
- 不把自动判断包装成用户已确认的事实。
- 如果自动创建或追加 Zoon 失败，保留本地 brief 并把失败原因写进状态。
- 每次输出必须包含 `推进阶段`、`模式来源`、`最早门槛`、`自动采用项`、`停止原因`、`下一技能` 和 `证据状态`。
- 如果继续用当前 run，输出当前 `run_id`；如果脚本不可用，写 `运行审计：未启用`。
