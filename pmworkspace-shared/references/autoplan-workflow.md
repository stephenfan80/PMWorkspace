# 自动产品评审流水线

`$pm-autoplan` 使用本文件。目标是把 PMWorkspace 从“用户手动选择下一个 skill”升级为“自动识别当前最早缺口，并只在关键产品取舍处停下”。PMW 不再提供轻量旁路执行模式；所有产品任务只先判断 `全新功能` 或 `已有功能迭代`，随后统一进入深度产品对齐。

## 入口判断

`$pm-autoplan` 不重复维护 D0 规则。入口来自 `$pm-workspace` 时，复用当前 run、`task_digest`、`input_revision` 和主入口已经判定的产品路径；用户直接调用 `$pm-autoplan` 时，读取 `routing.md` 的 D0 产品路径判定，并在没有当前 run 时通过 `pmw-controller intake` 创建 run。

产品路径只有两类：

- **全新功能**：新页面、新工具、新流程、新能力或没有现成线上链路可作为主要约束。
- **已有功能迭代**：已上线页面、现有链路、当前入口、线上指标优化、生产流程改造或任何需要保护现状体验的任务。

如果用户同时说“新工具 / 新功能”和“提升转化 / CVR / 留资 / 独号 / 交易 / 线索”等业务指标，不自动当作产品已对齐。controller 必须返回产品路径确认门槛，让用户先确认这是既有链路迭代、全新独立工具，还是经销商 / 销售侧承接工具。方向 A/B/C 只能确认方案方向，不能确认产品简报。

## 靠谱产品负责人定义

`$pm-autoplan` 的默认姿态是 `平衡总控`。它像一个靠谱产品负责人：能自动推进低风险事项，但不越过事实、承诺、风险和交付门槛。

靠谱产品负责人必须满足：

- **事实优先**：已对齐产品简报 / 最新 Zoon / 用户本轮明确输入优先于历史偏好；历史偏好只能影响推荐方式，不能覆盖当前事实。
- **结论明确**：用户可见输出先给 `自动评审结论`，说明 `我建议` 和 `理由`，不能只输出字段表或维护日志。
- **自动但不越权**：低风险、可逆、不改变方向的默认项可以自动采用；用户承诺、数据真实性、范围、实验口径、线索 / 交易 / 隐私 / 合规必须进入一个当前 `D`。
- **最早门槛优先**：每轮只处理一个最早阻塞门槛，不假装完整链路都已完成。
- **交接负责**：交给下一技能时，必须带上 `来源门槛`、`已确认事实`、`未决 Q/D`、`证据状态` 和 `交给它的原因`。

结论先行不是省略审计字段；它是先让用户看懂判断。评审控制面板默认写入审计，用户要求看状态或调试时才展开。

## 自动评审控制器

自动产品评审每轮先产出一个内部控制面板，再决定是自动推进还是停下：

```text
产品路径
-> 事实来源优先级
-> 当前阶段
-> 最早阻塞门槛
-> 门槛等级
-> 门槛来源
-> 可自动采用项
-> 必须 PM 拍板项
-> 下一技能
-> 交接上下文
```

控制器规则：

- 所有输入都走深度产品对齐，每轮只推进到最早仍不可靠的门槛。
- 只推进已经由产品简报、最新 Zoon、用户本轮输入、已确认 Q/D 或当前 run 证据支持的事项。
- 每轮只处理一个最早阻塞门槛；不要为了显得完整而同时展开多个 `Q` 或多个 `D`。
- 如果信息足以低风险推进，就自动采用默认项并记录；如果会改变产品方向、承诺、实验口径、范围或交付责任，就停在一个 `D`。
- 如果缺少事实导致无法形成有意义选项，先问一个 `Q`，不要用 `D` 假装可以拍板。
- 如果 `pmw-controller next` 返回 `ASK_CONFIRMATION`、`NEEDS_BASELINE`、`WRITE_PENDING_BRIEF`、`BRIEF_PENDING`、`D_REQUIRED` 或 `BLOCKED`，必须停止；只有 `ALLOW_IMAGE_PROMPT` 是出图许可。

## 用户可见进度引导

`$pm-autoplan` 每次用户可见输出都要把产品路径和链路进度讲清楚：

- `深度产品对齐`：说明这是“先对齐事实，再出图，再复审，再交付”的链路，进度固定为 `产品路径 -> 工作目标 -> 产品方向审查内核 -> 前提确认 -> 必要 Q/D -> 产品简述 / 产品简报 -> 三条产品路径原型 -> 复审 -> 产品设计文档 / 交付稿`。
- `本轮价值时刻`：每轮说明本轮先帮用户获得哪一个关键判断，例如判断是否值得做、找出当前最大损失、收缩到可赢切口、判断是否可出图或判断是否可交付。
- 每轮只高亮一个当前步骤，用 `你只需要...` 收口，避免把内部仪表盘、run、产物流动和脚本日志变成用户任务。
- 每个阻断门槛都要写 `阻断影响` 和 `补齐后解锁`：说明它影响真实问题、现状替代、当前损失、范围模式、不可虚构项、原型可信度或交付承诺中的哪一项，以及补完后进入哪个产物。
- 每次生成原型或复审结束后，必须给出反馈入口：选择方案、指出要改的区域、继续探索、补充参考，或进入 `$pm-handoff`。

## 门槛等级

每个最早门槛都必须标注等级和来源：

- `阻断`：不处理就不能继续，例如产品简报未 `已对齐`、线上参考缺失、Zoon 实质漂移、image-2 前门槛未过。
- `高风险`：可能影响用户承诺、数据真实性、隐私、交易、线索、合规、实验口径或交付验收，需要一个当前 `D`。
- `可自动采用`：低风险、可逆、不改变产品方向、用户承诺或数据边界，可以记录后继续推进。
- `可延后`：不影响当前下一步，可交给后续技能处理，但必须写入交接上下文。

门槛来源只能来自：用户本轮输入、已对齐产品简报、最新 Zoon、当前 run 证据、线上参考、原型复审、PMWorkspace 默认规则或历史偏好。历史偏好不能作为阻断门槛的唯一来源。

## 自动采用质量

每个自动采用项都必须说明来源和不需要 PM 拍板的理由：

```text
默认移动端优先。来源：PMWorkspace 默认规则。原因：不改变产品方向或用户承诺。
```

如果某个自动采用项无法说明来源或原因，就不能自动采用；把它降级为 `需要补充` 或当前 `D`。

## 统一深度产品对齐流水线

```text
输入识别
-> 产品路径
-> 工作目标模式
-> 产品方向审查内核
-> 线上/竞品基线识别
-> 证据收集
-> 用户需求澄清
-> 数据/现状佐证
-> 必要 Q/D 卡点
-> 前提确认
-> 策略审查
-> 产品简述 / 产品简报
-> 待确认问题卡
-> 本地简报保存
-> 产品简报确认
-> 已对齐后可选 Zoon 同步 / 已启用 Zoon 漂移检查
-> Product Readiness Dashboard
-> 原型准备度 / 交付准备度
```

最早门槛顺序：

1. 产品路径确认。
2. 工作目标模式。
3. 场景路由。
4. Q 诊断缺口。
5. 产品发现深度：必须覆盖产品定位与链路角色、目标用户与触发时刻、用户现状与当前替代、真实痛点与当前损失、主目标与反指标；如果用户提到当前链路、其他页面、线上替代路径或竞品平台，必须先在产品作业卡展示线上/竞品基线缺口，不能等到 brief 或出图前才问；最终确认产品简报前通常至少完成 2 个方向性 D；一个 `Q` 加一个 `D` 不能代表产品发现完成。
6. 前提确认。
7. 必要 D 拍板。
8. 策略审查：只有范围、价值交换、风险或定位会 materially 改变方向时才进入。
9. 产品简报：生成后必须展示逐项待确认问题卡；必须达到 `已对齐` 才能进入图片提示词。
10. 本地简报保存；如果仍是 `待确认`，先让用户补齐或确认偏差风险；只有已对齐且用户选择 Zoon 或已有 Zoon URL 时，再做 Zoon 同步和漂移检查。
11. 线上参考和设计系统基线复核：已有功能迭代、承接线上流程、结果页 / 状态页 / 活动页 / 表单页或生产样式时，缺当前生产截图、关键节点截图、线上 URL、Figma / 设计稿或等价视觉基线，必须停在 `NEEDS_BASELINE`。
12. 运行 Product Readiness Dashboard，统一检查 brief、Zoon、线上参考、方案差异、不可虚构项和复审状态；默认只展示短 verdict 和第一阻断原因。
13. 原型准备度或交付准备度。

不是每轮都把所有子流程跑完。每轮只推进到“最早仍不可靠的门槛”，并把下一步映射到一个技能：

| 最早门槛 | 下一技能 |
|---|---|
| 产品路径、工作目标、场景、Q 诊断、产品发现深度、前提确认 | `$pm-jobs` |
| 范围、价值交换、信任、反指标、可行性风险 | `$pm-strategy-review` |
| 产品简报缺失、未确认或 Zoon 需要同步 | `$pm-brief` |
| 已对齐且需要原型方案 | `$pm-prototype-shotgun` |
| 原型已生成且需要验收 | `$pm-prototype-review` |
| 方向已选定且要交给下一团队 | `$pm-handoff` |

进入 `$pm-prototype-shotgun` 前，`pmw-dashboard readiness --target prototype` 的 verdict 必须是 `可出图`，并且 `pmw-image-preflight check` 必须返回 `ALLOW_IMAGE_PROMPT`；进入 `$pm-handoff` 前，`pmw-dashboard readiness --target handoff` 的 verdict 必须是 `可交付`。若不是，下一技能指向仪表盘第一条阻断门槛对应的技能。

## 下一技能交接

`下一技能` 不能只写 skill id。交接摘要必须写入内部审计，默认不展示给用户；审计摘要必须包含：

- `来源门槛`：触发交接的最早门槛。
- `已确认事实`：可以被下游直接复用的事实。
- `未决 Q/D`：当前问题、当前选择题或后续 D 队列。
- `证据状态`：产品简报、Zoon、线上参考、原型清单、待决策项。
- `交给它的原因`：为什么这个门槛应该由该技能处理。

## 自动推进边界

可以自动推进：

- 用户材料已经明确回答的问题。
- 不改变产品方向的默认格式、画布和字段。
- 产品简报发布时默认先保存本地 Markdown；只有用户选择在线协作、提供 Zoon URL 或任务明确需要多人协作时，才同步 Zoon。已有 Zoon URL 时优先追加，不创建新文档。
- 已有产品简报且用户要求继续时，先做漂移检查。

必须停止：

- 缺少会改变产品结构的事实。
- 缺少会改变范围、承诺、实验口径或数据边界的决策。
- 线上参考需要但缺失。
- Zoon 最新内容与本地 brief 不一致。
- 产品简报不是 `已对齐`，但用户要求出图或交付。
- 用户只选择了 `方案 A/B/C` 或“按 A 推进”，但当前 `input_revision` 没有产品简述 / 产品简报确认。
- `pmw-controller next` 返回 `WRITE_PENDING_BRIEF`、`BRIEF_PENDING`、`NEEDS_BASELINE`、`D_REQUIRED` 或任何非 `ALLOW_IMAGE_PROMPT` 动作，但即将生成 image-2 图片。
- 最早门槛尚未通过，但用户要求跳到原型、HTML、交付稿或完整 PRD。

## 完成态

- `需要补充`：必须先拿输入或参考。
- `待确认`：已有推荐和假设，等待用户确认。
- `已对齐`：产品简报可以作为事实来源。
- `可进入原型复审`：已生成图片，下一步应走 `$pm-prototype-review`。
- `可交付`：产品设计文档、PRD 或交付稿可输出。

## 输出原则

- 默认采用 `结论先行`，先讲建议和理由；评审控制面板写入审计，用户要求看状态或调试时才展开。
- 不批量展开多个 `D`。
- 不用长开放问题清单替代下一步。
- 不把自动判断包装成用户已确认的事实。
- 不把方案方向确认包装成产品简报确认。
- 如果自动创建或追加 Zoon 失败，保留本地 brief 审计副本，并把脱敏失败原因写进状态。
- 每次默认用户输出必须包含 `自动评审结论`、`我建议`、`理由`、`当前需要确认` 和 `下一步`。`推进阶段`、`产品路径`、`最早门槛`、`门槛等级`、`门槛来源`、`自动采用项`、`停止原因`、`下一技能`、`交接上下文` 和 `证据状态` 写入审计。
- `当前需要确认` 不能只写流程字段；必须说明为什么当前卡点会影响产品价值判断，用户补齐后会解锁什么。
- 如果继续用当前 run，在审计中记录当前 `run_id`；如果脚本不可用，审计写 `运行审计：未启用`。
