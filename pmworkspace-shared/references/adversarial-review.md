# 产品方向审查

`$pm-strategy-review` 使用本文件挑战产品方向。它不是工程计划的长审查，也不重新做 `$pm-jobs` 的完整事实诊断，不替 `$pm-brief` 写产品契约；它只做 PMW 需要的产品方向审查：前提挑战、现状替代、不做推演、路径对比、范围模式和当前 `D`。

目标不是默认堆更多功能，而是帮助 PM 判断本周期应该扩大、选择性扩大、保持、收缩还是转向，并把任何范围或承诺变化变成用户显式拍板。

边界：

- 不重新做 `$pm-jobs` 的完整事实诊断。
- 不替 `$pm-brief` 写产品契约。
- 不展开研发能力依赖长清单；`$pm-strategy-review` 只判断能力前提是否会改变方向、范围或承诺，详细数据 / 接口 / 算法 / 后台 / 运营依赖在 `$pm-handoff` 的研发可行性反问中处理。

## 审查结构

每次策略审查都按这个顺序推进：

```text
前提挑战
-> 现状替代
-> 不做推演
-> 路径对比
-> 最大策略矛盾
-> 如果现在直接做会错在哪里
-> 范围模式
-> 本周期验证
-> 本周期验证价值
-> 产品动作
-> 当前 D / 后续 D 队列
-> 下一技能
```

不可跳过规则：

- `$pm-strategy-review` 接住 `$pm-jobs` 或 `$pm-autoplan` 交出的策略门槛：范围、价值交换、信任/风险、反指标、可行性、定位或业务冲突。
- 如果缺少用户、问题、主目标、反指标或不可虚构项等基础事实，退回 `$pm-jobs` 问一个 `Q`，不要虚构事实。
- 如果某项审查没有明显问题，写 `无明显问题` 或在审计里标记已覆盖，不能直接略过。
- 路径对比必须先于范围模式；不能只有一个默认方案。
- 如果事实足够，但不同选择会改变范围、价值交换、用户承诺、实验口径、信任风险、可行性边界或交付责任，展开一个完整 `D` 并停止。
- 不新增工程 11 段审查；产品方向只审影响 brief、原型和交付承诺的产品判断。
- 用户可见输出必须把最大策略矛盾翻译成 `如果现在直接做会错在哪里`，说明直接进入 brief、原型或交付会误伤真实问题、价值交换、反指标、不可虚构边界或本周期承诺中的哪一项。

## 路径对比

进入范围模式前，必须给 2-3 条路径：

- `最小路径`：本周期最小可赢切口，验证真实问题或关键行为。
- `增强路径`：在当前方向上增加 1-2 个高杠杆能力，提升价值交换或信任。
- `收缩 / 转向路径`：砍掉非关键范围，或改到更接近真实问题的新主路径。

每条路径必须说明：解决什么损失、牺牲什么、验证信号、失败信号、不可虚构项。

## 范围模式

策略审查必须显式选择一个范围模式。范围模式不是标签，而是本轮审查姿态；选择后不得漂移。

- **扩大模式：** 当前方向太小，无法解决真实损失或无法形成足够价值交换。默认动作是提出 1-2 个能显著提高价值的扩展，但每个扩展都必须标注前提、风险、反指标和不可虚构边界。
- **选择性扩大模式：** 当前范围作为基线，只把 1-2 个高杠杆机会交给用户挑选；被拒绝或延后的机会进入判断演进，不污染当前 brief。
- **保持模式：** 当前方向基本正确，问题在表达、顺序、信任或局部取舍。默认动作是保留核心范围，只调整信息层级、价值交换、风险标注或优先级。
- **收缩模式：** 当前范围过宽、用户任务不聚焦、第一版交付风险过高或反指标容易被破坏。默认动作是删除、后置或实验验证非关键范围，保留最小可赢切口。
- **转向模式：** 当前方向和真实问题、目标用户、现状替代或可交付能力不匹配。默认动作是提出新的主问题或主路径，并说明旧方向为什么不应继续进入产品简报。

选择规则：

- 如果最大策略矛盾来自价值不足或需求被低估，优先考虑 `扩大模式` 或 `选择性扩大模式`。
- 如果当前方向基本正确，但只有少数机会值得挑选，优先考虑 `选择性扩大模式`。
- 如果最大策略矛盾来自范围蔓延、交付不可控、反指标风险或第一版不可验证，优先考虑 `收缩模式`。
- 如果最大策略矛盾来自错误用户、错误任务、错误价值交换或错误业务目标，优先考虑 `转向模式`。
- 如果当前方向能解决真实问题，且风险主要来自呈现顺序、边界标注或局部取舍，优先考虑 `保持模式`。

## 时间推演

时间推演用于提前暴露实施和验证时会遇到的决策，不生成长计划：

- 单功能、原型、线上功能优化默认 `1-2 周`：第 1 天要明确什么、第 1 周验证什么、第 2 周如何判断继续或停止。
- 跨模块、大功能或产品线规划使用 `1-3 个月`：第 1-2 周验证什么、第 1 个月形成什么能力、第 2-3 个月如何扩展或收缩。

单功能交付和原型不得把 1-3 个月规划写成本周期承诺；只能放入下一步或待验证。

## 产品方向审查控制器

```text
来源门槛
-> 已确认事实
-> 前提挑战
-> 现状替代
-> 不做推演
-> 路径对比
-> 最大策略矛盾
-> 范围模式：扩大模式 / 选择性扩大模式 / 保持模式 / 收缩模式 / 转向模式
-> 建议姿态：扩大 / 选择性扩大 / 保持 / 收缩 / 转向
-> 本周期验证：1-2 周 / 1-3 个月
-> 本周期验证价值：<验证后能决定继续、收缩、删除、转向还是进入交付>
-> 产品动作：删除 / 前置 / 后置 / 标注 / 禁止 / 实验验证
-> 当前 D / 后续 D 队列
-> 下一技能
```

控制器规则：

- 每次必须输出：`我不赞成什么 / 我建议什么 / 为什么 / 本周期怎么验证 / 当前 D`。
- 每轮必须指出一个最大策略矛盾，例如价值交换不成立、范围过宽、承诺不可交付、反指标被破坏、业务目标损害用户信任。
- 每轮必须输出 `如果现在直接做会错在哪里`，把最大策略矛盾翻译成直接执行的产品风险，而不是只列抽象风险点。
- 每轮必须输出一个 `范围模式`，并说明该模式如何处理范围、价值交换、反指标和不可虚构边界。
- `建议姿态` 必须说明理由，不能只写扩大、选择性扩大、保持、收缩或转向标签。
- `本周期验证价值` 必须说明 1-2 周或 1-3 个月验证结束后，PM 能做出哪个判断：继续、收缩、删除、转向、进入原型或进入交付。
- 每个审查视角必须落成一个产品动作：删除、前置、后置、标注、禁止或实验验证。
- 策略 `D` 必须包含推荐项、选项、风险、会影响什么、进入产品简报的写法。
- 策略审查完成后，默认下一技能是 `$pm-brief`；如果仍缺事实，下一技能是 `$pm-jobs`；如果产品简报已对齐且只是复审方案方向，下一技能可以是 `$pm-prototype-shotgun` 或 `$pm-handoff`。
- 交给 `$pm-brief` 时必须带上 `范围模式`、选中路径、策略决策、最大策略矛盾、范围外、用户承诺边界、反指标保护、本周期验证和对原型的影响。

## 审查视角库

按当前场景选择 3-5 个视角，不跑固定清单。

### 问题真实性

- 这是用户真实痛点，还是团队发明的功能愿望？
- 什么观察行为证明痛点存在？
- 如果产品什么都不做，会发生什么真实损失？

### 具体用户

- 谁最强烈需要这个能力？
- 什么触发场景让问题变得紧急？
- 任务失败时这个用户会损失什么？

### 现状替代

- 用户现在靠什么 workaround 解决？
- 新方案必须赢过速度、信任、完整度、价格、习惯还是社交证明？
- 当前替代在哪里失败？

### 价值交换

- 用户付出的注册、手机号、付款、授权或长流程成本是否值得？
- 高成本动作前能先展示什么价值？
- 行动后结果会更具体、更可靠，还是只是更重？

### 信任与数据可信度

- 哪些数据是实时、估算、推断、用户提供或人工确认？
- 什么 caveat 必须可见才诚实？
- 怀疑型用户会挑战什么？

### 可行性与交付

- 屏幕承诺的能力今天能交付吗？
- 哪些需要人工确认、合作方数据、库存、政策或后台能力？
- 哪些能力不应出现在原型或验收标准里？

### 业务冲突与指标游戏

- 业务目标是否伤害用户信任？
- 哪个指标可能变好但真实用户结果变差？
- 需要哪个反指标保护投诉、留存、任务成功率、成本或合规？

### 边界情况

- 缺失、空、过期、矛盾数据时显示什么？
- 用户不符合资格、已完成任务或中途改变主意时怎么恢复？
- 不确定性如何呈现？

### 设计系统与层级

- UI 是否复用现有组件，而不是发明新形状？
- 用户第一眼、第二眼、第三眼分别看到什么？
- 哪些元素没有赚到自己的像素，应该删掉？

## 转成设计选择

产品方向审查只有改变 brief、原型或交付边界才有价值。把发现转成以下产品动作：

- `删除`：从本周期范围移除，或从原型中删除。
- `前置`：放到高成本动作、留资、支付或权限请求之前。
- `后置`：移到结果页、二级页、抽屉、后续步骤或实验后。
- `标注`：标注估算、不确定、人工确认、数据新鲜度或适用范围。
- `禁止`：不可虚构、不可承诺、不可写入验收或不可出现在原型里。
- `实验验证`：不进入稳定承诺，只进入实验假设、观察指标或后续验证。
