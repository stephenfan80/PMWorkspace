# 产品简报交接

首次引导、场景路由、决策门槛和产品追问之后使用本文件。生成原型前，产品简报必须已对齐。

这个资产是自适应产品设计简报，不是固定 PRD。它的作用是让产品意图可编辑、可确认、可复用，并能安全交给设计或产品协作者。它是产品思考与图片生成之间的对齐门槛。

For Chinese users, call this artifact `产品简报` in user-facing output. Keep internal status tokens only when needed, and pair them with Chinese labels such as `草稿`、`待确认`、`已对齐`。

## 产品核心信息契约

`$pm-brief` 的核心职责是生成产品核心信息契约：把上游事实、价值判断、策略取舍和参考门槛压缩成能指导原型、复审和交付的关键产品判断。

产品简报不是 PRD、会议纪要或信息仓库。它不追求把所有材料平铺完整，只保留会改变原型结构、复审判断、交付范围或用户承诺的核心信息。缺事实、缺策略拍板、Zoon 漂移或线上参考缺失时，仍停在对应门槛，不用简报补写事实。

用户可见输出默认先输出 `产品核心信息`，再输出 `产品简报门槛`，最后输出 `支持信息`：

- `产品核心信息`：一句话判断、目标用户 / 场景、核心问题 / 当前损失、当前替代方案、本次目标、反指标、策略选择、原型重点、不可虚构项。
- `产品简报门槛`：run、版本、确认状态、来源门槛、简报深度、缺失门槛、当前 D、下一技能和证据状态。
- `支持信息`：信息来源、事实/假设边界、线上参考、互联网案例启发、Zoon、已保存资产和必要证据记录。

支持信息可以保留信息来源、事实/假设边界、线上参考、互联网案例启发、Zoon、已保存资产，但不能压过核心判断。

简报深度不等于内容长度。快速版、标准版、深度版都使用同一套核心信息；深度版只在支持信息中增加证据、边界、决策记录和风险处理说明。

## 产品简报契约控制器

`$pm-brief` 先建立产品简报契约控制器，再决定写完整简报、停在确认题，或退回上游技能。控制器至少记录：

- `来源门槛`：来自 `$pm-workspace`、`$pm-autoplan`、`$pm-jobs`、`$pm-strategy-review`、Zoon、PRD、截图或用户本轮输入的哪一个门槛。
- `已完成门槛`：工作目标模式、Q 诊断、前提确认、D 拍板、线上参考、Zoon 同步或漂移检查中已经可靠的部分。
- `缺失门槛`：仍会改变产品事实、用户承诺、原型结构或交付责任的缺口。
- `事实/假设边界`：把已确认事实、当前假设、请补充、请拍板和不可虚构项分开写；历史偏好只能影响推荐语气，不能改变边界。
- `策略决策写入`：来自策略审查的取舍是否已经写进产品契约。
- `简报深度`：快速版、标准版或深度版，选择依据必须来自风险和证据状态。
- `下一技能`：继续停在 `$pm-brief`、退回 `$pm-jobs` 或 `$pm-strategy-review`，或进入 `$pm-prototype-shotgun` / `$pm-handoff`。
- `证据状态`：产品简报、Zoon、线上参考、截图/录屏、待决策项和当前 run 的状态。

事实优先级遵循 `pm-decision-principles.md`：已对齐产品简报或最新 Zoon 快照 > 用户本轮明确输入、截图、录屏或 URL 证据 > 已确认 Q / D / 前提 > 当前 run 证据 > 历史偏好。

如果来自 `$pm-jobs` 的基础事实仍缺失，下一技能是 `$pm-jobs`，只展开一个当前 `Q`，不能用产品简报补写事实。基础事实包括目标人群、核心问题、主目标、反指标、约束、数据可用性和不可虚构项。

如果来自 `$pm-strategy-review` 的取舍仍未拍板，下一技能是 `$pm-strategy-review`，只展开一个当前 `D`，不能把未决取舍写成已确认方向。

策略审查完成后，必须把范围模式和策略取舍写入 `对抗审查后的设计取舍`、`方案方向`、`范围外` 和 `决策记录`，并说明对原型内容重点、信任提示和不可虚构项的影响。

来自 `$pm-strategy-review` 的交接必须保留 `范围模式`、`策略决策`、`最大策略矛盾`、`范围外`、`用户承诺边界`、`反指标保护` 和 `对原型的影响`。如果这些字段缺失，产品简报只能标记为策略交接不完整，不能把策略取舍包装成已写入产品契约。

已对齐且用户要原型时，下一技能是 `$pm-prototype-shotgun`；已对齐且用户要交付时，下一技能是 `$pm-handoff`。如果只是生成或同步产品简报，输出 Zoon 与确认状态后停止。

## 产品简报前置闸门

产品简报是对齐后的记录，不是替代对齐的长计划。创建或更新产品简报前，必须已经完成：

1. `工作目标模式`：验证价值、优化线上指标、业务评审、设计评审或研发交付。
2. `Q 诊断`：关键诊断维度已被覆盖，包括目标人群与使用场景、核心问题与当前损失、本次目标与反指标；如果原型内容或约束边界仍不清楚，最多追加到 5 个动态 Q。Q 不要求固定题号或固定问法，来源可以是动态 Q、用户原始输入、Zoon、截图或线上参考。如果答案仍模糊，只在当前 Q 内追问一次，不写长简报。
3. `前提确认`：输出 2-4 条关键产品前提，让用户同意、不同意或修改。
4. `D 拍板`：如果存在会改变用户承诺、原型范围、实验口径或交付稿的取舍，必须用选择题拍板。

未满足以上闸门时，只能输出短对齐摘要、一个 `Q` 诊断问题或必要的 `D` 拍板问题；不要输出完整 md 方案、原型提示词、HTML 或交付稿。

## 始终创建或更新产品简报

每个原型请求都要创建或更新产品简报。包含版本和确认状态，并选择最小可用格式；最小格式也必须保留同一套产品核心信息：

- **快速版产品简报：** 截图迭代、小范围页面改动，或单个产品/设计决策；核心信息短，但仍要写清目标用户、问题损失、反指标、原型重点和不可虚构项。
- **标准版产品简报：** 大多数产品原型请求，尤其是需要沉淀意图、约束、线上参考和策略选择的任务。
- **深度版产品简报：** 新功能、高风险流程、跨团队协作、证据不清，或涉及敏感数据/运营的任务；深度主要体现在支持信息、证据边界和决策记录，不把核心信息拉成长报告。

不要因为用户想快就跳过产品简报。追求速度的请求应转为“快速对齐产品简报”，明确列出假设，并设置确认步骤。

快速对齐也必须先确认最少前提：通常只列 1-3 条假设和一个关键确认问题。用户确认前，状态保持 `待确认`。

如果用户已经提供完整 Zoon 产品文档，创建简短对齐摘要，并把最新 Zoon 快照作为事实来源。否则产品简报生成后默认创建 Zoon 在线文档，供用户修改对齐。创建或更新成功后，自动在 Codex 内置浏览器中打开可编辑 URL。

## 版本与状态

每份产品简报都应包含：

- `产品简报版本`：从 `v1` 开始；当用户改变产品方向时递增。
- `确认状态`：`草稿`、`待确认` 或 `已对齐`。
- `信息来源`：对话、现有 Zoon 文档、新建 Zoon 文档、截图组，或用户提供的 PRD。
- `来源门槛`、`缺失门槛`、`简报深度`、`证据状态`：来自产品简报契约控制器。
- `事实/假设边界`：已确认事实、当前假设、请补充、请拍板、不可虚构项。
- `最近决策`：用户最新确认过的产品/设计决策。
- `产品核心信息`：一句话判断、目标用户 / 场景、核心问题 / 当前损失、当前替代方案、本次目标、反指标、策略选择、原型重点和不可虚构项。
- `目标人群 / 场景`：最需要这个产品或屏幕的具体人群和使用场景。
- `核心问题 / 当前损失`：用户卡点、当前损失、现状替代方案的短摘要。
- `互联网案例启发`：公开最佳实践或同类案例只保留可借鉴原则、不可照搬和对原型影响；参考来源放在支持信息。
- `原型内容重点`：屏幕必须展示、重点突出、可后置和不可虚构的内容。
- `已确认前提`：用户明确同意、修改后同意，或批准按假设继续的前提。
- `Zoon 文档`：产品简报对应的在线协作文档 URL；创建失败时写“创建失败”，并保留本地 Markdown。
- `浏览器打开状态`：`已打开`、`打开失败，可手动打开`，或 `未尝试（说明原因）`。
- `线上参考状态`：已提供线上参考、无线上参考已确认、缺失待补充，或不适用。

## 简报深度

选择最小可用深度。简报深度不等于内容长度；快速版、标准版、深度版都使用同一套核心信息。深度只代表证据和风险处理深度，不代表核心信息越写越长。

### 快速版产品简报

用于截图迭代和窄范围改动。

核心信息保持完整但极短，支持信息只补必要证据：

- 产品核心信息：一句话判断、目标用户 / 场景、核心问题 / 当前损失、当前替代方案、本次目标、反指标、策略选择、原型重点、不可虚构项。
- 产品简报门槛：确认状态、缺失门槛、当前 D、下一技能、证据状态。
- 支持信息：截图、线上参考、Zoon 或当前假设中真正影响改图的部分。

### 标准版产品简报

用于大多数产品原型任务。

核心信息仍保持精简，支持信息补齐来源、边界和对原型的影响：

- 产品核心信息。
- 产品简报门槛。
- 支持信息：事实/假设边界、线上参考、互联网案例启发、Zoon、已保存资产、已确认前提。

### 深度版产品简报

用于新功能、高风险产品选择、跨团队工作、敏感数据、交易/服务流程或证据不清的任务。

不能把核心信息扩写成长章节；只在支持信息里补充：

- 证据与当前行为
- 已考虑的替代方案
- 设计决策记录
- 开放问题
- 风险处理、用户承诺边界、验收写入边界和后续 D 队列

## 对齐门槛

在写图片提示词或生成原型图片前，产品简报必须通过以下信号之一达到“已对齐”：

- 用户在对话中确认产品简报。
- 用户编辑或批准 Zoon 产品简报，并要求使用最新版本。
- 用户明确说使用产品简报中列出的假设，并且前提确认已经完成。

如果页面需要线上参考，必须先满足：用户已提供参考，或明确确认没有线上参考并批准按概念稿推进。

如果没有这些信号，分享产品简报或 Zoon 链接后停止，并请用户确认或编辑。状态不是 `已对齐` 时，不写 image-2 提示词、不生成图片、不生成 HTML、不输出交付稿。

## 前提确认

产品简报必须记录经过确认的产品前提。前提不是事实罗列，而是会影响原型的判断，例如用户真实问题、主目标与反指标、承诺边界、最小有价值版本或方案方向。

```text
前提确认：
1. <前提>。状态：已同意 / 已修改后同意 / 待确认。
2. <前提>。状态：已同意 / 已修改后同意 / 待确认。
3. <前提>。状态：已同意 / 已修改后同意 / 待确认。
```

只要任一关键前提是 `待确认`，产品简报确认状态不能写成 `已对齐`。

截图迭代时，快速版产品简报可以短到：

```markdown
## 快速对齐更新
- 工作目标模式：
- 产品意图不变：
- 请求改动：
- 保持不变：
- 约束：
- 前提确认：
- 请确认：按以上范围只改这些区域后，再用 image-2 出图。
```

## 场景模块

Add only the modules that fit the product. Do not include all modules by default.

### 转化流程

- 高成本动作前先展示价值。
- 区分必填信息和可选信息。
- 识别信任、投诉或退出风险。
- 设置反指标，避免低质量转化。

### 结果或报告页

- 结果页是否兑现了前置承诺。
- 数据可信度和新鲜度。
- 区分估算值和已确认值。
- 下一步动作和不确定性处理。

### 内部工具

- 重复任务和预期提效。
- 错误恢复和审计记录。
- 权限和角色边界。
- 空数据、部分数据、过期数据和失败状态。

### 交易或服务流程

- 资格判断和所需材料。
- 履约状态。
- 异常路径和恢复方式。
- 人工或合作方依赖。

### 内容或社区

- 创作或消费动机。
- 质量信号。
- 参与循环。
- 治理或滥用风险。

### 看板或数据分析

- 用户应该做的决策。
- 数据新鲜度。
- 对比基线。
- 提醒阈值或动作触发。

## 协作标记

使用这些标记，让 PM 知道哪里需要编辑：

- `当前假设：` 助手推断出来的内容。
- `请补充：` 缺失信息会明显改善原型。
- `请拍板：` 产品取舍需要决策。
- `不可虚构：` 设计中不能展示未支持的数据或功能。

## Zoon 交接

如果用户提供了现有 Zoon 文档：

- 除非用户要求新建文档，否则把产品简报追加到现有文档。
- 使用 Zoon 工作流和追加操作。
- 追加成功后，自动在 Codex 内置浏览器中打开该 Zoon 文档。
- 告诉用户：现有文档现在是下一步原型的事实来源。
- 图片生成前，请用户在对话中确认，或编辑 Zoon 产品简报。
- 如果用户在 Zoon 或对话中改变方向，递增产品简报版本，重新运行相关决策门槛，并用 `pmw-log brief <功能名>` 重新同步。

如果没有现有 Zoon 文档：

- 默认使用 `pmw-log brief <功能名>` 保存产品简报；它会自动调用 `pmw-zoon sync`，没有 Zoon URL 时再创建文档。
- 也可以直接使用 `pmw-zoon create --title "产品设计简报：<功能名>"` 新建 Zoon 文档。
- 创建成功后，用 `pmw-project link-zoon <url>` 保存到本地项目记录。
- 创建成功后，自动在 Codex 内置浏览器中打开可编辑 URL，方便用户直接编辑。
- 只把返回的可编辑 `url` 发给用户，不展示 API 原始响应。
- 不暴露 `ownerSecret`、原始 token 或 API 响应内部信息。

如果 Zoon 创建失败：

- 在对话中提供产品简报 Markdown。
- 简短说明“Zoon 创建失败，可稍后重试”，并继续保存本地资产。

如果 Zoon 已创建但浏览器打开失败：

- 仍返回 Zoon URL。
- 写明 `浏览器打开状态：打开失败，可手动打开`，并保持 Zoon 文档字段为已创建的 URL。

## 生成原型前

当可编辑 Zoon 产品简报存在且用户已确认：

1. 生成图片前重新读取最新 Zoon 快照。
2. 先运行 `pmw-zoon drift --url <Zoon URL>`；若返回 `DRIFT`，把最新 Markdown 作为产品事实来源并更新 brief 版本。
3. 用 PM 编辑更新产品意图、约束和提示词内容。
4. 不只依赖过期的对话历史。

`DRIFT` 如果改变目标、反指标、不可虚构项、范围、用户承诺或方案方向，不能继续标记为 `已对齐`；先把漂移写入缺失门槛，并回到 `$pm-jobs` 或 `$pm-strategy-review` 处理一个当前 `Q` / `D`。

同时检查 `线上参考状态`：

- `已提供线上参考`：把截图/录屏/相似页面摘要写入图片提示词。
- `无线上参考已确认`：按概念稿推进，并在原型计划里说明视觉基线是假设。
- `缺失待补充`：停止，不写 image-2 提示词，先向用户索取参考。
- `不适用`：继续使用默认生产基线或用户提供的设计系统。
